# Structured Product Workflow／結構型商品作業流程

## 繁體中文

狀態：FCN Workflow 視窗的九個分頁都已實作：1 每日匯入（交易明細與每日股價進最小 FCN 資料庫、回補股價 CSV）、2 起單資料（讀起單建檔、在視窗裡確認後匯入、匯入後算出核對條件）、3 準備（從商品資料夾挑出 TS／IIS、標準命名、Word 轉 PDF）、4 核對（從資料庫讀條件、核對完寫回）、5 放回、6 寄信草稿（只建 Outlook 草稿、不寄出）、7 人工維護（補齊、更正商品條件與交易明細）、8 進度（每檔商品的作業進度、篩選與匯出）、9 出場清單（某一個收盤日出場的 KO、接股、到期還本、顧客贖回）。本機開發、公司電腦試用中，正式驗收（[驗收流程](docs/checker/acceptance.md)）尚未完成；自動寄信、EXPRESS FCN／BEN、公司伺服器協作尚未授權，見[待定事項](docs/open-questions.md)。

本專案管理正式 Order、建檔、上手文件歸檔、核對串接及 FC 寄送。詢價端沿用既有系統。
核對規則原本在獨立的 [fcn-term-sheet-checker](https://github.com/TaylorYam/fcn-term-sheet-checker)，已併入本專案（[ADR 0005](docs/adr/0005-merge-checker-into-workflow.md)）：程式與歷史在 `src/fcn_checker/`，同一次安裝就有 `fcn-batch`、`fcn-panel`，核對文件在 [docs/checker/](docs/checker/README.md)；新商品資料改由 Order、交易明細與股價建立（[ADR 0006](docs/adr/0006-new-product-data-from-order.md)）。

### TS／IIS 批次準備

從公槽 FCN 底下以 TDCC 命名的商品資料夾，挑出中文產品說明書與中文投資人須知，改名成核對工具要的 `<TDCC>_TS.pdf`、`<TDCC>_IIS.pdf`，放進新開的批次資料夾。商品資料夾裡的檔案只讀不改。

**作業人員安裝（Windows）**：先安裝官方 Python 3.11 以上（包含 Tcl/Tk），把專案放到自己有寫入權限的資料夾，再建立 PostgreSQL 資料庫與日常帳號，並在專案安裝資料夾放好 `.env`，最後雙擊 `setup_panel.cmd`。安裝會建立專案自己的 `.venv`、依 `constraints.txt` 安裝套件（需要連到公司允許的 Python 套件來源），並以安裝資料夾的 `.env` 執行資料表遷移；需要管理者密碼時會在安裝視窗詢問。遷移失敗會中止安裝並顯示錯誤，修正連線或權限後重新執行即可。看到「安裝完成」後，雙擊桌面或專案資料夾裡的「FCN Workflow」捷徑開啟作業視窗；捷徑建立失敗時改雙擊 `launch_panel.cmd`（`launch_checker_panel.cmd` 開同一個視窗並停在「4 核對」）。日常操作不用打指令；上次選的資料夾與視窗大小記在安裝資料夾的 `.local/`，核對紀錄寫在安裝資料夾的 `runtime/核對紀錄/`。搬移資料夾或更新程式後請重新執行安裝；重跑前先關閉 FCN Workflow 視窗，視窗還開著時安裝會停下並提示（[#110](https://github.com/TaylorYam/structured-product-workflow/issues/110)）。安裝一開始會印出目前的程式版本（branch 與 commit）；資料夾不在 `main`、或 `main` 落後 `origin/main` 時會提醒先 `git checkout main`、`git pull` 再重跑，提醒不會中止安裝（[#136](https://github.com/TaylorYam/structured-product-workflow/issues/136)）。Word 轉檔需要這台電腦裝有 Microsoft Word。

**作業視窗**：一個「FCN Workflow」視窗，左側步驟欄照每天的順序排：1 每日匯入 → 2 起單資料 → 3 準備 → 4 核對 → 5 放回 → 6 寄信草稿 → 7 人工維護（需要時才用）→ 8 進度 → 9 出場清單，按一下就切到那一步，目前所在的那一步用淺藍底標出；切換時各頁內容都保留。畫面是淺灰底、白色卡片的簡潔風格：每頁上方寫這一頁的功能，貼 TDCC 的欄位是直的、底下顯示「已貼 N 筆」；做完先列重點數字（例如已準備／跳過、通過／不一致），有問題的數字用紅色，狀態列變成綠色結果條（[#83](https://github.com/TaylorYam/structured-product-workflow/issues/83)、[#85](https://github.com/TaylorYam/structured-product-workflow/issues/85)）。除了「4 核對」，每頁結果表右上方有「全部複製」，一鍵把整張表（含表頭）放進剪貼簿，貼到 Excel 會照格子分開，不會換掉正在看的那一列；在表上按右鍵可以只複製一格（例如 TDCC）或一列。點過表之後，Ctrl+A 全選（反白，右邊正在看的那一檔不會換）、Ctrl+C 複製選取的列，右鍵也可以複製選取的列；「7 人工維護」的檢查結果表只能用右鍵和「全部複製」。「4 核對」的結果表沒有「全部複製」，可以按右鍵或 Ctrl+C 複製（上方的說明書清單也能 Ctrl+A）（[#121](https://github.com/TaylorYam/structured-product-workflow/issues/121)）。欄位比畫面寬時，結果表下方的左右捲軸可以捲到最右邊的欄（[#179](https://github.com/TaylorYam/structured-product-workflow/issues/179)）。結果表的欄寬依內容自動調整：表上的列有變動就重算，每一欄是表頭與內容最寬的那個，太長的內容（例如原因）只算到一個上限，其餘左右捲動或右鍵複製；輸入日期的欄位（8 進度的交易日、9 出場清單的收盤日、登記顧客贖回與批次登記已寄出的日期、審查通過日期）旁邊有「日曆」按鈕，點一天就填入 YYYY-MM-DD，也照樣可以直接打字（[#192](https://github.com/TaylorYam/structured-product-workflow/issues/192)）。商品資料夾所在的根目錄在視窗最上方設一次（按「變更…」），3 準備、6 寄信草稿兩頁共用；各頁的輸出位置仍各自記住。做完一步，下一頁會先帶入結果，上方藍色提示條寫出帶入了什麼（按「改選…」可以換掉）；完成訊息旁出現「下一步 →」，按了才切頁，也不會自動開始：每日匯入完成 → 「2 起單資料」帶入這份交易明細的 FCN TDCC（依出現順序、不重複；TDCC 不是剛好 12 碼、整檔已取消的不帶；起單資料頁已有不同的 TDCC、或有改過還沒匯入資料庫的內容時先問，正在讀取或匯入時不帶入；帶入時清掉上一次讀取的結果）；準備完成 → 「4 核對」帶入這批已準備的 PDF（條件來源與參考條件表沿用核對頁目前選的；核對頁有還沒存檔的結果時先問）；核對存檔 → 「5 放回」帶入批次資料夾與剛存的核對結果檔；回補股價、匯入歷史收盤價比價完成 → 「9 出場清單」帶入比到的那一天。審查通過日期、匯出回報包、匯入歷史收盤價、重新比價全部、匯入舊商品的價格與比價日、信箱維護、發行機構評等與使用的設定檔不是每天的步驟，在視窗上方的「維護」選單（[ADR 0007](docs/adr/0007-single-workflow-window.md)）。關閉視窗時，核對頁還在處理、有還沒存檔的核對結果，起單資料頁還在處理、有改過還沒匯入資料庫的內容，或人工維護頁還在處理、有改過還沒存檔的內容，會先提醒。第一次開啟時最大化，之後照上次調整的大小開啟。

**從兩個捷徑的版本更新**：重新執行 `setup_panel.cmd` 後，桌面與專案資料夾只剩「FCN Workflow」一個捷徑，開啟時停在「1 每日匯入」（以前停在核對）。以前建的「TS IIS 準備與放回」捷徑，指向這個專案資料夾的會自動刪掉，指向別的資料夾的不動（[#77](https://github.com/TaylorYam/structured-product-workflow/issues/77)）。

**從舊的核對工具安裝移過來**：以前另外裝過 `fcn-term-sheet-checker` 的電腦，在本專案資料夾執行一次 `setup_panel.cmd`，之後改用「FCN Workflow」捷徑；桌面上舊的「Term Sheet 核對」捷徑還指向舊資料夾，請手動刪除。兩邊各用自己資料夾裡的 `.venv`，不會互相影響。舊資料夾 `runtime/核對紀錄/` 裡的核對紀錄要留查時，整個複製到本專案的 `runtime/核對紀錄/`（檔名是日期時間，不會重複）；核對 PANEL 記住的選檔資料夾不會帶過來，第一次重新選即可。確認新的捷徑能用之後，舊資料夾可以刪掉。

**開發者安裝**：

```bash
python -m pip install -c constraints.txt -e ".[dev]"
```

PostgreSQL 驅動已包含在套件裡。核對程式（`fcn_checker`）也在同一個套件裡；如果這個 Python 環境以前另外裝過舊的 `fcn-term-sheet-checker`（套件名稱 `fcn-checker`），請先 `python -m pip uninstall fcn-checker`，避免兩份 `fcn_checker` 同時在 Python 路徑上。

開發時用指令開啟視窗（`fcn-panel` 開同一個視窗並停在「4 核對」）：

```bash
spw-panel
```

在「3 準備」分頁：

1. 在輸入框貼上要核對的 TDCC（換行、空白、逗號、頓號都可以分隔；重複的只算一次）。
2. 確認視窗最上方的根目錄（商品資料夾可以在底下任何一層；要換時按「變更…」），再選輸出位置；兩者都會記在本機 `.local/`，下次直接帶入。
3. 按「開始準備」。每次在輸出位置開一個 `待核對_<日期時間>` 資料夾，已存在就不做。
4. 看第一頁內容判斷：開頭附近出現「中文產品說明書」或「中文投資人須知」；說明書第一頁要有資料夾的 TDCC，投資人須知有 12 碼代號時要相符。檔名只當參考。
5. 有上手 PDF 就用 PDF；某種文件沒有 PDF 時（例如 MS、BNP 只給 Word），才把資料夾裡的 Word（`.docx`、`.doc`）複製到暫存區，用 Microsoft Word 轉成 PDF 再判斷（[ADR 0002](docs/adr/0002-word-to-pdf-with-microsoft-word.md)）。原始 Word 不動；轉檔失敗或逾時（Word 跳出對話框）時那個商品跳過。MS 說明書封面的「受託機構商品代號：」固定空白，轉檔前在暫存複本補上 TDCC（已有值不動），不用再手動改 Word；商品資料夾裡的原始 Word 仍是空白，放回與寄信用的是補好的 PDF；準備清單的原因欄會寫「已補受託機構商品代號」（[#56](https://github.com/TaylorYam/structured-product-workflow/issues/56)）。
6. 說明書或投資人須知任一份找不到、或有兩份以上候選時，整個商品跳過並寫出原因與候選檔名。
   **重新核對上手修正版**：資料夾裡上次放回的「_待確認」檔不當候選，只用來認出哪一版沒通過（比對全文）；內容相同的幾份只算一份。上手寄來新版時會挑新版，連上次已放回的標準名舊版也一併換掉（修正版沿用舊檔名、覆蓋了舊原檔也一樣：內容不同時上手檔名的版本優先，只以標準檔名存在的內容當成上次放回的舊版）；上手還沒寄新版時，沿用上次沒通過的那一版照常準備（原因寫「沿用上次沒通過的版本」；資料夾裡若另有封面商品代號不符或轉檔失敗的新檔，也會一起寫出），所以改過參考條件表或核對規則後，可以用同一版重複核對；同一版又沒通過時，錯訊和資料夾裡最新的錯訊檔不同才會再寫一份。準備清單的原因欄會寫出排除了哪些舊版。MS、BNP 這類只給 Word 的上手，只有沒通過的那份會換成新版；如果兩份都改了，請先把舊的標準名檔移到子資料夾。上次沒通過的是 PDF 時，修正版也要有 PDF 才會被挑到（例如 JPM 同時給 PDF 和 Word，修正版只有 Word 時請上手補 PDF）。
7. 批次資料夾裡的 `準備清單.xlsx` 記錄每份文件的來源檔、是否由 Word 轉檔、輸出檔名、SHA-256 指紋、狀態與原因。完成後可以按「打開批次資料夾」查看；按「下一步：核對 →」切到「4 核對」，這批已準備的 PDF 已經帶入，條件來源預設資料庫，直接載入預覽（選 Excel 時先選好參考條件表）。
8. **同時留步驟紀錄**（[#151](https://github.com/TaylorYam/structured-product-workflow/issues/151)、[ADR 0019](docs/adr/0019-progress-step-records-and-lifecycle-events.md)）：`.env` 有資料庫連線設定時，每個已準備的商品在資料庫多一筆「已準備」紀錄（誰、什麼時候、準備清單），之後進度頁靠它判斷走到哪一步；跳過的不寫，同一檔重新準備多一筆。沒有連線設定或取消登入時照樣準備、不留紀錄；連不上或寫入失敗時準備清單照常產出，完成訊息寫出原因。作業人員更新時由安裝器自動套用資料表版本 0015。

核對完、存下核對結果檔後，按「下一步：放回 →」切到「5 放回」分頁：

1. 批次資料夾與「4 核對」剛存的核對結果檔已經帶入（要換時按「選擇…」或提示條的「改選…」）。
2. 按「放回資料夾」。核對結果檔「回填後」上 `TS/IIS完成檢核` 為 `V` 的商品（說明書與投資人須知都通過或人工放行）用標準檔名放回；「錯誤清單」上沒通過的那份，檔名最後加「_待確認」放回（例：`<TDCC>_TS_待確認.pdf`），同商品通過的那份仍用標準檔名，原因欄附上錯訊；同時在商品資料夾寫一份 `<TDCC>_錯誤訊息_<日期時間>.xlsx`（一條錯訊一列，附 PDF 頁碼，頁碼對應放回的「_待確認」檔），打開資料夾就看得到問題在哪裡。重複放回、待確認檔已經在時不會再寫。核對結果檔裡沒出現的商品（還沒核對）不放回。
3. 放回前重算批次裡 PDF 的指紋，和準備清單不符就不放。商品資料夾已有同名檔：內容相同（位元組相同，或全文相同，例如同一份 Word 重新轉出的 PDF）算「已在」（例如 UBS 本來就給標準檔名），內容不同不覆蓋、整個商品不放回，由作業人員決定留哪份。
4. 只複製，批次資料夾保留；結果寫在批次資料夾的 `放回清單_<日期時間>.xlsx`；這批準備了但還沒核對的商品也會列出，標「不放回」。修好未通過的商品、重新核對後可以再放一次，已放回的會顯示「已在」；改用標準檔名放回時，舊的「_待確認」檔和舊錯訊檔不會自動刪除，清單會提醒你確認後手動刪除。
5. **同時留步驟紀錄**（[#151](https://github.com/TaylorYam/structured-product-workflow/issues/151)、[ADR 0019](docs/adr/0019-progress-step-records-and-lifecycle-events.md)）：放回或已在的每個商品多一筆「已放回」紀錄（含放回「_待確認」檔的，結果寫「含待確認」與兩份的狀態），不放回的不寫；連線設定與失敗時的做法同「3 準備」。

### TS／IIS 核對

核對程式（`src/fcn_checker/`，原 [fcn-term-sheet-checker](https://github.com/TaylorYam/fcn-term-sheet-checker)）把中文產品說明書與中文投資人須知 PDF 跟參考條件表逐欄比對：14 家上手、固定規則、不使用 LLM。同一檔的兩份都通過或人工放行，才輸出到核對結果檔的「回填後」（`TS/IIS完成檢核` 打 `V`，回填 ISIN、發行日、比價日；VWAP 商品另回填各標的價格）；沒通過的每條錯訊列在「錯誤清單」。上面的「放回資料夾」讀的就是這份核對結果檔。

1. 在「4 核對」分頁選條件來源（預設資料庫；選 Excel 時再選參考條件表），再選批次資料夾裡的 `<TDCC>_TS.pdf`、`<TDCC>_IIS.pdf`，按「載入／重新載入預覽」→「開始核對」。看過錯訊認定沒問題的可以「人工放行」，最後按「儲存核對結果…」。載入預覽後，上方說明與選檔區會收成一行摘要，讓預覽與核對結果有更多空間；要改條件來源或 PDF 時按摘要旁的「變更…」展開（[#108](https://github.com/TaylorYam/structured-product-workflow/issues/108)）。有未通過的商品時，可以從「維護」→「匯出回報包…」交給維護者。
2. 指令版：`fcn-batch <參考條件表.xlsx> <PDF…> --out <輸出資料夾>`，一次完成預覽、核對與儲存，不能人工放行。結束碼 0 是已涵蓋的規則全部通過（沒涵蓋的項目仍要人工看）、1 有不一致或需人工覆核（含未支援上手）、2 錯誤。
3. 每次儲存另寫一份內部核對紀錄（程式版本、設定與每份 PDF 的指紋、逐項結果），PANEL 寫在安裝資料夾的 `runtime/核對紀錄/`，指令版寫在執行目錄的 `runtime/核對紀錄/`。
4. **從資料庫讀條件**（[#68](https://github.com/TaylorYam/structured-product-workflow/issues/68)、[ADR 0013](docs/adr/0013-check-from-database.md)）：「條件來源」選「資料庫」就不用選參考條件表。載入預覽時依 PDF 檔名的 TDCC 從資料庫產生一份同格式的參考條件表（留在安裝資料夾的 `runtime/資料庫參考條件表/`），之後的核對、人工放行、核對結果檔與回報包都和 Excel 一樣。原本預設 Excel，[#108](https://github.com/TaylorYam/structured-product-workflow/issues/108) 起預設資料庫；選資料庫時「參考條件表」那一列收起來。
   - 資料庫沒有這檔、商品條件缺必填欄（[#114](https://github.com/TaylorYam/structured-product-workflow/issues/114)）、核對條件還不是「完成」（等股價、等交易明細、待確認，見下面「核對條件」），或以前清單更新匯入、已鎖住的商品：那一份不核對、需人工覆核並寫原因，不能人工放行，同批其他照常。
   - 按「儲存核對結果…」存好核對結果檔後寫回資料庫：說明書與投資人須知都通過或人工放行的商品，回填 ISIN、發行日、比價日（VWAP 商品另含各標的價格），人工放行時單位面額改成 TS 的值，然後**鎖住**（之後起單資料不能再覆蓋）。核對之後條件又被改過（例如重新匯入起單資料）的商品不回填、不鎖住，請重新載入預覽再核對。每份文件最新的核對結果與每個改變的原值都留在資料庫。已鎖住的商品可以再核對，但不再回填。
   - 寫回失敗（例如連線中斷）時核對結果檔照樣保留，畫面寫出原因，排除後按「重新寫回資料庫」。
   - 指令版：`fcn-batch --database <PDF…> --out <輸出資料夾>`（連線設定讀 `.env`，沒寫密碼時會問；產生的參考條件表放在輸出資料夾）。
   - 作業人員更新程式時重新執行 `setup_panel.cmd`，安裝器會自動套用尚未執行的資料表版本；開發環境手動遷移請使用 `spw-db-migrate --env-file .env --admin-user postgres`。

規則、範本、支援範圍、參考條件表格式與核對的 ADR 見 [docs/checker/](docs/checker/README.md)（只有中文，裡面的 Issue 編號指原 repo）；新增上手或範本改版依[新增上手流程](docs/checker/issuer-onboarding.md)。

### 每日匯入（最小 FCN 資料庫）

把每天的 FCN 交易明細與每日股價匯入 PostgreSQL（[#87](https://github.com/TaylorYam/structured-product-workflow/issues/87)、[ADR 0008](docs/adr/0008-daily-prices-denomination-and-order-dates.md)）；商品條件改由「2 起單資料」確認後匯入；信箱在資料庫直接維護（[ADR 0004](docs/adr/0004-mailbox-maintained-in-database.md)、[#35](https://github.com/TaylorYam/structured-product-workflow/issues/35)）（[#32](https://github.com/TaylorYam/structured-product-workflow/issues/32)、[ADR 0003](docs/adr/0003-minimal-fcn-database.md)）。寄信草稿之後只讀這個資料庫。

**第一次設定（每台電腦一次）**：
1. 安裝 PostgreSQL，建立資料庫與日常使用的帳號（可用 `scripts/provision_postgres_dev.py`）。
2. 在安裝資料夾（開發時是 repo 根目錄）建立 `.env`，填 `PGHOST`、`PGPORT`、`PGDATABASE`、`PGUSER`；`PGPASSWORD` 可以不填，匯入時會詢問。`.env` 不進 Git。
3. 作業人員安裝時，`setup_panel.cmd` 會用有建立權限的帳號建立資料表，並把讀寫權限給 `PGUSER`。開發環境或需手動遷移時，明確指定 repo 的 `.env`：

```bash
spw-db-migrate --env-file .env --admin-user postgres
```

作業程式更新後重新執行 `setup_panel.cmd`，安裝器會套用尚未執行的版本；開發環境則重新執行上面的指令。換電腦（例如從筆電到公司電腦）時不複製資料庫，先建立資料庫、帳號與 `.env`，再執行安裝並重新匯入每日更新。

**每天**：
1. 打開每日更新（範本 `PostgreSQL每日更新.xlsx`，只放在私人樣本倉庫）：把前一天的交易整列貼到 `交易明細`（欄位同交易清單月份工作表，第 1 列欄名不要動）；`BBG_Data` 依範本取價（C1 是取價日，內容是前一個交易日的價格）。以前的 `清單更新` 工作表已停用，檔案裡有也不讀。
2. 視窗切到「1 每日匯入」，選每日更新，按「匯入」。
3. 每天匯 MarketData CSV（[#153](https://github.com/TaylorYam/structured-product-workflow/issues/153)、[ADR 0020](docs/adr/0020-close-prices-and-observation-rules.md)）：在「回補股價」選前一個交易日 Bloomberg 匯出的 `MarketData_YYYYMMDD.csv`，按「回補股價」。除了股價（見下面「回補前幾天」），同時把 CSV 那一天的收盤價存進收盤價表給比價用；忘了匯，比價會停在「等股價」。
4. 看結果：
   - 「新增交易」：寫入成功。「已存在」：之前匯過，這次沒有寫入。
   - 「內容不同（未覆蓋）」：交易列和資料庫裡的不一樣，資料庫保留第一次的內容。資料庫的值寫錯時在「7 人工維護」改（見下面「人工維護」），改到和 Excel 一樣後再匯入就是「已存在」。
   - 「擋下」：這一列缺值或寫法不認得，修正 Excel 後重新匯入。
   - 「股價衝突」：`BBG_Data` 同一個代碼出現多列、值不一樣；這個代碼的價格不存，算價格時不能用。值都一樣的重複列只算一筆。
   - 「股價不是數字」：價格格子不是數字（例如 `#N/A`），存成空白。
   - 「交易已取消」：交易明細的「備註」去頭尾空白、不分大小寫等於 `Cancel`，或備註包含「取消」；該列不會匯入資料庫。
   - 「名字對不到信箱」：交易明細的 FC 名字在 `mailbox.person` 找不到（大小寫不同視為同一人）；拼法不同請在 `mailbox.alias` 加一筆別名。
   - 「信箱尚未建立」：`mailbox.person` 還是空的，名字無法比對。
   - 完成訊息另外寫出股價的取價日與筆數；同一個取價日重新匯入時，整份取代那一天的股價（每次匯入都留紀錄）。
   - 「核對條件：…」：匯入後重算還沒鎖住的商品（見下面「核對條件」），列出這次有變、或還沒完成的商品。
5. 匯入完成後，這份交易明細的 FCN TDCC 已經帶到「2 起單資料」（完成訊息寫出帶了幾筆）；按「下一步：起單資料 →」接著讀起單建檔（[#90](https://github.com/TaylorYam/structured-product-workflow/issues/90)）。已存在的商品照樣帶；交易明細沒有 FCN 或整份不匯入時不帶。

**回補前幾天**（台灣放假或請假之後，[#112](https://github.com/TaylorYam/structured-product-workflow/issues/112)、[ADR 0015](docs/adr/0015-price-csv-backfill.md)）：BBG_Data 只抓得到最新的價格，所以交易明細和股價分開匯入。
1. 交易明細：照舊用每日更新，勾「只匯交易明細」再按「匯入」；不讀 BBG_Data、股價不動。
2. 股價：在「回補股價」選 Bloomberg 匯出的 `MarketData_YYYYMMDD.csv`（一次一個），按「回補股價」。CSV 的取價日是收盤那一天，存成**下一天**（10/16 收盤 → 取價日 10/17），等同隔天早上用 BBG_Data 取到的價格；那一天原本的股價整份取代。欄名要完全相同，取價日不是日期、不只一天或沒有任何代碼時整份不匯入；沒有 1日前收盤價，幣別、市值(百萬美元) 不存。匯入後重算核對條件，問題寫進 CSV 同資料夾的 `每日匯入錯誤.xlsx`。

**收盤價**（給比價用，[#153](https://github.com/TaylorYam/structured-product-workflow/issues/153)、[ADR 0020](docs/adr/0020-close-prices-and-observation-rules.md)）：以「實際收盤日＋代碼」存一筆，和上面以取價日為鍵的股價分開；BBG_Data 不寫收盤價（它的日期不明確）。
- 代碼去掉彭博最後的類別字（`AAA UW Equity` → `AAA UW`、`USDJPY Curncy` → `USDJPY`），其餘一字不差，和商品條件的標的寫法一致。
- 只存該代碼市場的交易日：週末、或交易所假日表（`config/exchange_holidays.toml`，有美國、日本、港股）上的休市日不存，CSV 在休市那天帶的前一天價格會略過。交易所不在假日表的代碼照存，之後由比價標待確認；交易所在假日表、但日期超出涵蓋範圍的（例如假日表從 2022-07-28 起，更早的歷史收盤價）不能確認是不是交易日，不存、列出來，補了那幾年的假日表再匯一次。
- 讀不到交易所假日表時，回補股價照樣匯股價，但收盤價這次不存（完成訊息會寫），修好假日表後再匯一次同一個 CSV。
- 同一（收盤日、代碼）再匯入整筆取代；值改了的，舊值留在 `workflow.close_price_change`。
- 去掉類別字後同一個代碼有不同的值（例如 `AAA UW` 與 `AAA UW Equity`），或股價衝突的代碼，收盤價不存。

**匯入歷史收盤價**（一次性，「維護」選單「匯入歷史收盤價…」）：選 HP 格式的 Excel（第一張工作表；第 3 列從 E 欄起是收盤日，第 4 列起每列一檔，C 欄是帶類別字的彭博代碼）。進度與結果顯示在「1 每日匯入」。
- 整份讀完、檢查完才寫入：第 3 列有不是日期的格子、收盤日重複、沒有收盤日或沒有任何代碼時整份不匯入；讀不到交易所假日表也不匯入。
- 錯誤值（`#N/A N/A`、`#N/A Requesting Data...`、`#N/A Invalid Security`、`-`、亂碼、失效公式）、空白與不是正數的格子一律當沒有價格。休市日的值不存；同一個代碼重複、同一天的值不同時不存。
- 問題依代碼與原因整理（第一天、最後一天、格數），寫到來源檔同資料夾的 `歷史收盤價錯誤_<日期時間>.xlsx`；`#N/A N/A` 只有落在確定的交易日才列。沒有問題時不寫。`#N/A Requesting Data...` 是抓價沒完成，要重抓再匯。
- 完成訊息寫出日期範圍、代碼數、沒有價格的格數（休市日不算）與錯誤清單的位置。

**比價**（[#155](https://github.com/TaylorYam/structured-product-workflow/issues/155)、[ADR 0020](docs/adr/0020-close-prices-and-observation-rules.md)）：回補股價與匯入歷史收盤價完成後自動跑，也可以按「維護」選單「重新比價全部」（不匯入，用收盤價表現有的價格）。核對條件「完成」的商品（已鎖住與未鎖住都比）逐日比到收盤價表最新的一天，算出的 KO、接股、到期還本寫成存續事件，每檔另存一筆比價狀態 `workflow.pricing_status`（在庫／等股價／待確認／已出場、原因、已比到的日期、是否鎖住）；都是和上一次不同才寫。
- KO：收盤價 ≥ KO 價。非記憶式要同一個觀察日所有標的都達標；記憶式每檔在任一觀察日達標就記住，全部記過就 KO。KO Type 每日型的觀察日是第一個比價日起到最終比價日、所有標的市場都開市的日子；每期型只看各期比價日；Non-Call 等於天期的不觀察 KO。
- KI：到期觀察（EKI）只看最終比價日，收盤價 < 下限價；每日觀察（AKI）看 Strike date 之後該標的市場的每個交易日；每期觀察（MKI）不比（比價日 1～12 只有 KO 的期數），KO 照比、比價狀態照 KO 算，KI 欄寫「MKI (manual)」；最終比價日沒有 KO 時待確認，要人工判定接股或到期還本（[#196](https://github.com/TaylorYam/structured-product-workflow/issues/196)、[ADR 0022](docs/adr/0022-pricing-status-is-ko-only.md)）。
- 到期（最終比價日沒有 KO）：沒有 KI 或 KI 曾觸及，且最差表現的標的（最終收盤價 ÷ 進場價最低）收盤價 < 執行價 → 接股（記那一檔）；否則到期還本。事件日是觸價或判定的觀察日。
- 某標的在它市場的交易日要用的價格不在收盤價表 → 停在那一天（已比到前一天），狀態「等股價」寫出標的與日期；補了價格下一次比價自然接上。交易所不在假日表、日期超出假日表涵蓋範圍、要比價了收盤價表卻完全沒有這個代碼、比價日是休市日、條件缺價格或比價日 → 待確認並寫原因。
- 已出場的不再比（[#169](https://github.com/TaylorYam/structured-product-workflow/issues/169)、[ADR 0021](docs/adr/0021-stop-observing-exited-products.md)）：已有存續事件的商品（比價算出的 KO、接股、到期還本，登記的顧客贖回，舊清單事件）狀態是已出場，原因寫出事件與事件日，已比到的日期沿用上一次，事件不再重算；先假設收盤價不會事後更正。核對條件後來不是「完成」的：已出場的照樣已出場，其他的狀態改待確認。已出場的商品在「7 人工維護」改了商品條件時，存檔結果提醒事件不會跟著改，和上手通知不同時到「8 進度」提出異議。
- 還在 Non-call 期間（第一個比價日之前）的在庫商品，比價原因寫「Non-call period（第一個比價日 YYYY-MM-DD）」；比價狀態、已比到、比價原因只講 KO：已比到在第一個比價日之前、不觀察 KO 的商品都空白；每日觀察 KI（AKI）照樣從 Strike date 隔天起每天比，缺它要的價格照樣等股價，原因後面寫「（每日觀察 KI）」。KI 另寫在進度頁的 KI 欄，用英文代碼：No KI、EKI、AKI、MKI (manual)，觸及時寫 `AKI hit 日期 標的`（第一次觸及）；已出場、沒存過 KI 的寫 KI 種類（[#198](https://github.com/TaylorYam/structured-product-workflow/issues/198)、[#196](https://github.com/TaylorYam/structured-product-workflow/issues/196)、[ADR 0022](docs/adr/0022-pricing-status-is-ko-only.md)）。Non-Call 等於天期的還沒到最終比價日時寫「還沒到最終比價日（YYYY-MM-DD）」（[#194](https://github.com/TaylorYam/structured-product-workflow/issues/194)）。
- 完成訊息列出比到哪一天、各狀態的檔數；結果表列出這次有變的存續事件與還沒完成（等股價、待確認）的商品，未鎖住的標「未鎖住」。比價失敗時匯入照樣保留，完成訊息寫原因。

**舊商品的價格與比價日**（一次性，「維護」選單「匯入舊商品的價格與比價日…」，[#154](https://github.com/TaylorYam/structured-product-workflow/issues/154)）：以前由清單更新建立、已鎖住的商品沒有各標的的四個價格和比價日，比不了價。選一份參考條件表格式的 Excel（例如回填後的庫存總表），進度與結果顯示在「1 每日匯入」，完成後照樣比價：
- 只處理資料庫已鎖住、還沒有標的價格或比價日的商品，缺哪一樣補哪一樣：UL_1～UL_5 的進場價、執行價、下限價、KO 價（代碼用資料庫的，表上的代碼要一樣，不分大小寫、空白與結尾的 Equity）與比價日 1～12（空值寫法存空白）；其他欄一律不碰。還沒有核對條件的，另寫一筆「完成」的核對條件（寫明來源檔），之後比價就會比這檔；已有核對條件的不動，不是「完成」時結果寫出來（比價不會比，要先處理）。
- 表上的「庫存狀態」：「已於 Y/M/D KO」寫成 KO 事件（事件日是那一天）、「到期還本」寫成到期還本事件（事件日是資料庫這檔的最終比價日，沒有最終比價日時空白；[#189](https://github.com/TaylorYam/structured-product-workflow/issues/189)），來源「舊清單」；已有同種事件的不重複寫（KO 日期不同時寫出來請人確認），已有別種事件的那一檔不匯入。表上沒有「庫存狀態」欄時只補價格與比價日。
- 表上沒有、資料庫沒有、還沒鎖住、表上有兩列、代碼和資料庫不同、價格不是數字、進場價／執行價／KO 價空白、比價日不是日期的：那一檔不匯入並寫出原因，其他照常；不匯入的另外寫一份 `舊商品補資料錯誤_<時間>.xlsx` 放在來源檔旁邊。缺必要欄時整份不匯入。
- 整次匯入一個 transaction；重跑同一份，補過的都是「已存在」，不重寫。

只收 FCN，其他商品略過並計數；備註為 `Cancel` 或包含「取消」的交易列不會匯入資料庫；同一份重複匯入不會重複寫入交易；任何錯誤都不會留下一半的資料。所有匯入問題會集中重建到來源檔同資料夾的 `每日匯入錯誤.xlsx`，包含既有匯入歷史；因此 9 月、10 月會在同一份檔案。交易列是否取消以備註欄為準，不讀取 Excel 底色。股價以「取價日＋代碼」為一筆，代碼只去頭尾空白，不改大小寫、不換交易所碼；`BBG_Data` 的 C1 不是日期或第 2 列欄名不同時整份不匯入。每日匯入不寫商品條件、不做分公司對帳，也不會修改信箱；分公司配置在匯入後重算核對條件時由交易明細算（#88）。#87 之前清單更新寫入的商品照舊保留，還沒鎖住的會一起重算。

**信箱維護**（[#158](https://github.com/TaylorYam/structured-product-workflow/issues/158)）：在視窗上方「維護」選單按「信箱維護…」，另開一個視窗：左邊列出人員（名字、信箱、單位、固定副本、別名），右邊列出別名（別名 → 人員）。按「新增人員…」「新增別名…」，或點一列再按「修改…」「刪除…」（雙擊也是修改）；按確定就存進資料庫 `mailbox.person`、`mailbox.alias`，並在 `mailbox.change_log` 記下誰、何時、改前改後。名字不分大小寫不能重複，信箱格式不對、別名重複（不分大小寫）、別名指到不存在的人都會被拒絕，原因寫在畫面上、不會存一半。改名時別名會跟著改；刪除人員會連帶刪掉他的別名（會先列出來問）。打開之後別人已經改過的那一列不會被蓋掉，請按「重新整理」再改。沒有任何固定副本時，畫面會提醒寄信草稿會停下來。

**發行機構評等**（[#237](https://github.com/TaylorYam/structured-product-workflow/issues/237)）：在「維護」選單按「發行機構評等…」，另開一個視窗：左邊列出各上手的發行機構與保證機構（上手、角色、名稱與目前的標準普爾／穆迪／惠譽評等、生效日），點一個機構，右邊列出它的歷次評等（新的在上面）。評等變了就點機構按「新增評等…」，填生效日與三家評等（沒有該家評等就留空，三家至少一家）；生效日要比最新一筆晚。只能「修改最新一筆…」「刪除最新一筆…」，每個機構至少留一筆。新上手按「新增機構…」（生效日空白表示不設起始日）。存進資料庫 `workflow.rated_entity`、`workflow.credit_rating`，並在 `workflow.credit_rating_log` 記下誰、何時、改前改後；格式不對（例如穆迪寫成 A+）會被拒絕，原因寫在畫面上。某個交易日用的評等是生效日在那天以前的最新一筆；第一批評等（2026-09～10 的 580 份說明書與投資人須知整理出的 14 家、18 個機構）生效日寫「最初」，任何交易日都適用。核對時（[#240](https://github.com/TaylorYam/structured-product-workflow/issues/240)）資料庫產生的參考條件表會帶出交易日當時的評等欄，14 家上手的說明書與投資人須知寫的評等都要和它相同：BARC（[#243](https://github.com/TaylorYam/structured-product-workflow/issues/243)）、HSBC、MS、DBS、Natixis、UBS 的發行機構評等，Citi、GS、BNP、BBVA 的發行機構與保證機構評等（[#242](https://github.com/TaylorYam/structured-product-workflow/issues/242)）、CA、JPM、Nomura、SG 的保證機構評等（[#241](https://github.com/TaylorYam/structured-product-workflow/issues/241)；發行機構是工具公司，文件寫明沒有評等就不核對，沒寫明或寫了評等轉人工覆核）（文件沒寫的評等機構不比；評等表沒有那個機構就轉人工覆核；規則見 `docs/checker/rules/shared-check-rules.md` §10）；做評等核對的上手（現在 14 家都做；新上手上線時評等核對還沒做的除外）核對後才改評等，寫回時會當成條件已變、不回填。

備用：也可以照舊直接在資料庫用 SQL 新增或修改（例如有寫入權限的帳號）；比對用的小寫鍵由資料庫自動產生，上面的檢查一樣有效，但不會留 `mailbox.change_log`。

若同一個 PostgreSQL 已有其他系統的 `public.mailbox`（例如欄位為 `user_name`、`email`、`unit`），本專案不會讀取或修改它。`public.mailbox` 是資料表；本專案使用的 `mailbox.person` 與 `mailbox.alias` 是本專案 migration 建立的另一個 schema／資料表集合，兩者可並存。若要把既有名單初次帶入本專案，請先檢查資料並由管理者明確執行一次性 SQL；不會自動同步，`fixed_cc` 也必須另外確認：

```sql
INSERT INTO mailbox.person (name, email, unit, fixed_cc)
SELECT user_name, email, unit, false
FROM public.mailbox
ON CONFLICT (name_key) DO NOTHING;
```

```sql
-- 新增人員（fixed_cc = true 是寄信的固定副本）
INSERT INTO mailbox.person (name, email, unit, fixed_cc) VALUES ('Amy', 'amy@example.com', 'FC', false);
-- 交易清單上的拼法不同時，加別名指到使用者名稱
INSERT INTO mailbox.alias (alias, person_name) VALUES ('Amie', 'Amy');
-- 修改、刪除
UPDATE mailbox.person SET email = 'amy.new@example.com' WHERE name = 'Amy';
DELETE FROM mailbox.person WHERE name = 'Amy';  -- 她的別名會一起刪除
```

### 寄信草稿

為核對通過的 FCN，在**自己的傳統版 Outlook 草稿匣**建立 TS／IIS 信件給承作的 FC（[#29](https://github.com/TaylorYam/structured-product-workflow/issues/29)）。**只建草稿，不會寄出**；請在 Outlook 逐封確認後自己按寄出。資料全部讀資料庫，所以先做完每日匯入。

1. 視窗切到「6 寄信草稿」，貼上核對通過的 TDCC（分隔方式同「3 準備」）。
2. 選結果清單位置（根目錄用視窗最上方的，同「3 準備」），按「建立草稿」。視窗會先顯示最近一次每日匯入（時間、第幾次、檔名），確認後才開始建立。
3. 每檔要符合才會建草稿，否則標「待處理」並寫出原因：
   - 資料庫有這檔的商品條件（信裡要用的必填欄沒有空白，[#114](https://github.com/TaylorYam/structured-product-workflow/issues/114)；期初價格空白時信裡空白）與交易列；
   - 商品資料夾裡有 `<TDCC>_TS.pdf` 與 `<TDCC>_IIS.pdf`（放回資料夾只會以標準檔名放回核對通過的文件；`_待確認` 檔不算）；
   - 交易列上的 FC 都對得到信箱。
4. 信件：一檔一封；收件人是承作的 FC（略過 PB，只有 PB 時標「不需寄送」），副本是信箱裡 `fixed_cc` 的人；主旨 `[中文TS/IIS] [FCN] - <TDCC>`；內文使用 `.env` 的 `SPW_MAIL_TEMPLATE` Excel 範本，填入資料後以可編輯表格貼進 Outlook；附上兩份 PDF。
   風險等級寫自算的等級（[#239](https://github.com/TaylorYam/structured-product-workflow/issues/239)，回填的是 RR4）；待算或還沒算過時寫「待確認」，草稿照樣建立，結果清單與畫面標出這一檔並寫出原因，寄出前請自己補上。
   表格內容置中；英文字型使用 Calibri、中文字型使用 Microsoft JhengHei；表頭最多兩行。固定副本排序為 MAX、BOB、PM，再接其他人員。
5. 結果清單 `寄信草稿清單_<日期時間>.xlsx` 列出每檔的狀態、收件人、副本與原因；「資料來源」工作表記錄用的是哪一次每日匯入（時間、編號、檔名、SHA-256）與搜尋時讀不到的資料夾。
6. **同時留步驟紀錄**（[#151](https://github.com/TaylorYam/structured-product-workflow/issues/151)、[ADR 0019](docs/adr/0019-progress-step-records-and-lifecycle-events.md)）：建了草稿的每檔多一筆「草稿已建立」紀錄（誰、什麼時候、結果清單）；待處理、不需寄送、建立失敗的不寫。寫入失敗時草稿與結果清單照常，完成訊息寫出原因。

每日匯入略過的非 FCN 商品會標「不支援的商品類型」。同一檔重跑會再建一封草稿，重複的請自己刪除。某一檔出錯（例如 Outlook 沒回應、資料有問題）只標那一檔「建立失敗」，其他檔照常處理。商品資料夾只讀不改。作業人員更新程式後重新執行 `setup_panel.cmd` 即會套用新增的資料表版本；開發環境請用上面的手動遷移指令。

### 起單資料

讀作業人員每天的起單建檔 `起單建檔_<日期>.xlsm`，在視窗裡逐檔確認、修改後匯入資料庫（[#97](https://github.com/TaylorYam/structured-product-workflow/issues/97)、[ADR 0010](docs/adr/0010-order-terms-from-daily-order-sheet.md)；確認畫面見 [#86](https://github.com/TaylorYam/structured-product-workflow/issues/86)、[ADR 0009](docs/adr/0009-confirm-order-terms-in-window.md)）。不再讀 `(Order)` 原信，也不再匯出 Excel。

1. 視窗切到「2 起單資料」，貼上 TDCC（分隔方式同「3 準備」；剛做完每日匯入時已帶入交易明細的 FCN TDCC，按提示條的「改選…」可以清掉自己貼），在「起單建檔」按「選擇…」選當天的檔（第一次打開 `G:\Bond Data\PM事項\0.常用工具\ELN每日起單建檔`，之後打開上次選的資料夾），按「讀取」。這一頁不用根目錄。
2. 只讀選的那一份、不修改它。起單建檔只有一張工作表，前幾列裡有 `TDCC` 的那列是表頭（目前第 2 列、從 B 欄開始）；欄位依表頭文字對，不分大小寫、不看位置。讀的欄：Product、Currency、Guaranteed Periods (m)、BBG Code 1～5、Strike (%)、KO Type、KO Barrier (%)、Coupon p.a. (%)、`UF (%)`（舊表頭 `Upfront / NotePrice (%)`）、Tenor (m)、Barrier Type、KI Barrier (%)、四個日期、期初價格。其他欄（No.、Observation Frequency、OTC、Funding Spread、Effective Date Offset、起單FC）沒有對應的資料庫欄位，不讀。
3. `UF (%)` 那欄放的是價格（例如 97.14），畫面上叫 Upfront / NotePrice (%)；寫進資料庫時 UF = 100 − 價格。
   Strike date（期初定價日，[#101](https://github.com/TaylorYam/structured-product-workflow/issues/101)、[ADR 0011](docs/adr/0011-strike-date.md)）起單建檔沒有這欄：期初價格寫「明日開盤價」時，期初價格記成開盤價、Strike date 是交易日之後標的市場的下一個營業日（依 `config/exchange_holidays.toml`，例如週五交易是週一；遇到休市日再往後）；其他情況 Strike date 等於 Trade date。假日表確定不了（標的交易所不在表上、日期超出範圍）時 Strike date 留空標紅，由作業人員填（不會用資料庫的值補）；Strike date 不能早於 Trade date。畫面上改 Trade date 時，原本等於 Trade date 的 Strike date 會跟著改，明日開盤價算出的不動。
4. 規則式、不猜值：
   - KO Type 要是 Daily／Daily Memory／Period End／Period End Memory，Barrier Type 要是 NONE／EKI／AKI，期初價格要是 開盤價／收盤價／VWAP，不分大小寫（`DAILY MEMORY`、`None` 都認）。
   - 認不得的值（例如 `MKI`、KO Type 寫成數字、期初價格寫「待確認」）、數字欄不是數字、日期欄不是日期：那格留空、標紅，寫出讀到的值，由作業人員在畫面上改。
   - 上手依 TDCC 前三碼查 `config/issuer_prefixes.toml`；查不到時擋匯入。
   - 同一檔 TDCC 有好幾列：內容一樣就用；不同的欄留空，寫出各列的值，填好才可以匯入（正確是空白時請改起單建檔後重新讀取）。
   - 貼的 TDCC 不在這份檔裡標「找不到」；不是 12 碼標「待確認」。
   - 選到的檔有好幾張工作表（例如總表 `ELN每日起單建檔.xlsm`）、找不到表頭、少欄或同一欄出現兩次時，整批不開始並寫原因。
5. 讀完後，下面左邊列出這批商品（有問題的排前面），右邊是編輯區：
   - 狀態：「待確認」是有欄位擋匯入（必填空白、格式不對等）；「請確認」是讀起單建檔時有提醒、但可以匯入；「可匯入」；「已鎖住」是核對通過、或 migration 0006 時已在資料庫的商品，不能改也不能匯入（要改用「7 人工維護」，見下面「人工維護」）。找不到的照舊顯示原因。
   - 點一檔，右邊列出上面那些欄。淺紅底是擋匯入或讀起單建檔時有問題，下面寫原因；淺黃底是和資料庫的值不同，寫出資料庫的值，可以按「用資料庫的值」改回。KO Type、Barrier Type、期初價格用下拉選單，日期寫成 `2026-10-21`；離開欄位或按 Enter 時檢查，寫錯的保留打的字並標紅，匯入時那一檔不匯入、其他照常。
   - `.env` 有連線設定時會連資料庫（沒寫密碼時讀取前會問一次）：資料庫已有、還沒鎖住的商品（包含清單更新建立的），起單建檔空白的欄帶入資料庫的值（好幾列不同的欄除外）。沒有連線設定也照樣可以讀，只是不帶入；讀取時沒連上資料庫的商品，匯入時不會覆蓋資料庫裡已有的那檔（請重新讀取）。
6. 確認好按「匯入資料庫」：通過檢查的寫進資料庫（單位面額依幣別預設值；最終比價日、到期日必填；核對通過前重新匯入會覆蓋並留紀錄，紀錄寫起單建檔檔名與列號、和起單建檔不同的人工修改；空白的欄不會蓋掉你沒看過的資料庫值），結果欄改成新增／覆蓋／沒有變／不匯入／已鎖住，「核對條件」欄是匯入後重算的狀態，「風險等級」欄是同時算出的 RR（見下面「核對條件」的「風險等級」）；選一檔按「風險等級明細…」看計算明細。承作金額以交易明細為準，這裡不填。資料表版本 0008 會把既有商品的 Strike date 補成交易日；更新時安裝器會自動套用尚未執行的 migration（開發環境請用上面的手動遷移指令）。有改過、還沒匯入資料庫就重新讀取、帶入新的 TDCC 或關閉視窗時會先問；處理中編輯區不能改。
7. 鎖住後要改條件，改在「7 人工維護」（見下面「人工維護」）；原本這一頁的「更正商品條件…」已拿掉。

### 人工維護

找出還缺資料的商品，手動補齊或修改資料庫裡的商品條件（[#115](https://github.com/TaylorYam/structured-product-workflow/issues/115)、[ADR 0017](docs/adr/0017-manual-maintenance-tab.md)）與交易明細（[#116](https://github.com/TaylorYam/structured-product-workflow/issues/116)、[ADR 0018](docs/adr/0018-maintenance-trade-rows.md)）。已鎖住商品的更正（[#55](https://github.com/TaylorYam/structured-product-workflow/issues/55)、[ADR 0014](docs/adr/0014-term-correction.md)）也在這裡做。

1. 視窗切到「7 人工維護」，按「檢查」：列出還沒鎖住、缺起單資料必填欄的商品，和交易明細有、資料庫還沒有商品條件的 TDCC（狀態「只有交易明細」），依 TDCC 排；上方寫缺資料幾檔、其中只有交易明細幾檔。表格一格一格列出上手、狀態與必填欄，缺的格子淺紅底；欄位多時左右捲動，TDCC 欄固定在左邊。已鎖住的不列（鎖住前一定齊全）。
2. 點一檔打開，或在 TDCC 欄輸入任何一檔按「打開」（包括已鎖住、沒缺資料的；交易明細和資料庫都沒有的不能打開）。右邊是和「2 起單資料」同一套的編輯區，上方寫這檔存檔時怎麼處理。改過的欄（包含清空、補上的）標黃並寫出資料庫的值，可以一鍵改回。
   - 還沒鎖住：帶出資料庫目前的值。必填欄可以先空著（淺紅底，寫「缺，可以先存、之後再補」），商品種類除外；格式錯、欄位之間對不上照起單資料匯入的規則擋存檔，有 KI 時 KI Barrier (%) 照舊必填（還不確定就把 Barrier Type 也先空著）。上手不能改；幣別改了時單位面額換成新幣別的預設值。
   - 只有交易明細：從空白開始，商品種類 FCN，上手依上手編號對照（查不到時擋存檔），單位面額依幣別預設值。存檔時新增商品條件，來源「人工維護」；之後重新匯入起單資料時照常整檔覆蓋。
   - 已鎖住：照更正的規則：不能留空白，Issue date 由 TS 回填、不能改，上手不能改，幣別改了時單位面額換成新幣別的預設值。存檔後商品維持鎖住（重新匯入照樣不覆蓋）、核對結果不動；算過核對條件的商品，改到標的、比例、Strike date、期初定價、幣別、交易日、UF 這類欄位時重算價格與交叉比對（VWAP 保留 TS 回填的價格，只重算比例改了的；換了標的的位置空白並標待確認），只改 Coupon、到期日等不重算。
   - 交易明細：商品條件底下依資料庫的列序（「第 n 列」）列出這檔的交易明細，欄位同每日匯入；只有交易明細的那檔也一樣。只改值，不能新增、刪除列，備註也不能改成 Cancel 或「取消」。打的字照每日匯入的規則解讀，交易日期、幣別、金額、FC/PB、分公司必填，空白或寫錯標紅、擋存檔；改過的格子同樣標黃、可以一鍵改回。沒改的格子照資料庫的值，不擋存檔。改了的 FC 名字照每日匯入的規則比對信箱，對不到時標紅字提醒（寄信草稿會找不到這位 FC），但可以存檔。
3. 按「存檔」（原因選填）：商品條件與交易明細一起存。還沒鎖住的寫進資料庫並重算這一檔的核對條件（缺欄時停在待確認；只有交易明細、還沒有商品條件的不重算），重算失敗時整次不寫入；已鎖住的只改交易明細時，改到交易日期、幣別、金額、分公司、UF 才重算，商品照樣維持鎖住、核對結果不動；完成訊息列出改了什麼、重算後的狀態與對不到信箱的 FC 名字，檢查結果表跟著更新（補齊的那檔拿掉）。存檔後畫面換成資料庫存的值，可以接著改、再存。
4. 每次存檔在 `workflow.term_correction` 留一筆：存檔前後的值（含改變的價格）、存檔前的商品欄位（新增時空白）、Windows 使用者名稱、時間、原因，`locked` 記存檔時是否已鎖住。沒有改任何欄位時不寫入；打開之後資料庫的這檔被改過、被鎖住（核對通過），或別人已經建了這檔的商品條件時不寫入，請按「重新載入」。改了交易明細時另外在 `workflow.trade_row_correction` 留一筆：改了哪些格（第幾列、欄、存檔前後）、存檔前這檔的交易明細、使用者、時間、原因，已鎖住的商品只改交易明細時也記重算後改變的價格。打開之後這檔的交易明細被改過（例如重新匯入多了一列）時也不寫入。有改過還沒存檔就打開別檔、重新載入或關閉視窗時會先問。之後的每日匯入照舊不覆蓋資料庫。更新程式後重新執行 `setup_panel.cmd`，安裝器會自動套用資料表版本 0014（開發環境請用上面的手動遷移指令），以前的紀錄不變。
5. **匯出商品條件**（[#122](https://github.com/TaylorYam/structured-product-workflow/issues/122)）：按「檢查」旁的「匯出商品條件…」，選存放位置與檔名（預設 `workflow_product_<日期時間>.xlsx`，從上次匯出的資料夾開始），把資料庫目前的 `workflow.product` 整張匯出成 Excel：第 1 列是資料庫的欄名，最後多一欄「存續狀態」（在庫／KO／接股／到期還本／顧客贖回，取最新一筆存續事件，[#152](https://github.com/TaylorYam/structured-product-workflow/issues/152)、[ADR 0019](docs/adr/0019-progress-step-records-and-lifecycle-events.md)；舊的 `status_event` 等四欄已由資料表版本 0020 移除，[#172](https://github.com/TaylorYam/structured-product-workflow/issues/172)），依 TDCC 排序，日期、數字照型別寫入，TDCC 等文字保留前導零。只讀資料庫，不改任何資料；畫面上還沒存檔的修改不在匯出檔裡（完成訊息會提醒）。同名檔開在 Excel 等寫不進去時顯示原因，原本的檔案不動。

### 進度

「8 進度」列出每檔商品在哪一個作業進度（[#156](https://github.com/TaylorYam/structured-product-workflow/issues/156)、[ADR 0019](docs/adr/0019-progress-step-records-and-lifecycle-events.md)）。按「重新整理」讀資料庫；篩選與排序只在畫面上做，不再讀資料庫。
- 範圍：有交易明細或有商品條件的 TDCC，一檔一列。
- 作業進度由資料庫的事實依序推出，每檔只有一個，共五個階段（[#186](https://github.com/TaylorYam/structured-product-workflow/issues/186)）：有「已寄出」就是完成；以前清單更新建立、已鎖住的舊商品還沒有步驟紀錄的，以前在 Excel 走完，也算完成（#184）；否則依序是資料準備中（核對前的三件有任一件沒齊：交易明細、商品條件、股價，三件平行、沒有先後）→ 待核對（三件都齊、還沒有核對結果）→ 待修正（有核對結果、還沒鎖住）→ 待寄信（已鎖住、還沒有「已寄出」）。三件齊的判斷：有這檔的交易明細；有商品條件而且不缺必填欄（每個標的都已有進場價時，期初價格空白不算缺，#182）；核對條件是完成。準備、放回、建草稿等各步日期只顯示，不決定階段。
- 欄位：TDCC、上手、交易日、距今天數、作業進度、交易明細／商品條件／股價（三件齊了打勾，缺哪一件一眼看得出來）、存續狀態、比價狀態（[#170](https://github.com/TaylorYam/structured-product-workflow/issues/170)：在庫、等股價、待確認、已出場，比價時還沒鎖住的標「（未鎖住）」；還沒比過的空白）、已比到（KO 已比到的日期）、比價原因、KI（[#196](https://github.com/TaylorYam/structured-product-workflow/issues/196)、[ADR 0022](docs/adr/0022-pricing-status-is-ko-only.md)）、異議（還沒解除的異議）、各步日期（交易明細匯入、商品條件匯入、核對條件完成、已準備、核對、鎖住、已放回、草稿已建立、已寄出；同一步多筆取最新）、卡住的原因（例如還沒有交易明細、缺的必填欄、核對條件待確認的原因、核對結果；缺幾件就寫幾件）。卡住的、比價狀態是等股價或待確認的列用紅字。
- 篩選：交易日區間（YYYY-MM-DD，空白是不限；有區間時沒有交易日的不列）、作業進度、存續狀態與比價狀態（多選，都不勾是全部；勾了比價狀態時還沒比過的不列）、上手。預設依距今天數由大到小，落後的在上面；點欄名排序，再點一次反過來，空白一律放最後。
- 「匯出 Excel…」：把目前篩選、排序後的整張表寫成 Excel（預設 `作業進度_<日期時間>.xlsx`，從上次匯出的資料夾開始），欄位同畫面。先寫暫存檔再換名；同名檔開在 Excel 等寫不進去時顯示原因，原本的檔案不動。
- 人工能做的三件事只在這一頁登記（[#157](https://github.com/TaylorYam/structured-product-workflow/issues/157)），先在表上選商品（可以按住 Ctrl 或 Shift 多選）；都在背景寫資料庫、留誰與何時，一檔寫不進去只影響那一檔並寫出原因，寫完自動重新整理：
  - 「登記已寄出」：選中的每檔寫一筆「已寄出」步驟紀錄，進度變完成。寫之前先到資料庫查哪幾檔登記過：都沒登記過時問一次確認；有登記過的另外問：是＝也再寫一筆、否＝只寫還沒登記過的、取消＝都不寫。
  - 「批次登記已寄出…」（#186）：寄信由其他人負責時，一次補登「某天以前的都寄完了」。填一個交易日（必填，YYYY-MM-DD），重新讀資料庫，找出交易日在這天以前（含）、目前是待寄信（核對通過、還沒登記已寄出）的商品，先列出幾檔、哪些 TDCC，確認後各寫一筆「已寄出」；其他階段的一律不動，寫的時候已經登記過的不重複寫。寫的時候已經解鎖的也跳過。完成後狀態列提示同一個日期範圍裡還沒核對完、這次沒有登記的檔數（沒有交易日的商品，例如還沒有交易明細的，不在任何日期範圍裡，不算）；沒有待寄信的商品時不寫。不用先在表上選商品。
  - 「登記顧客贖回…」：填事件日（必填，YYYY-MM-DD）與備註，選中的每檔寫一筆來源「人工」的顧客贖回事件；已有存續事件的那一檔不能登記並寫出原因。登記後比價不再比這檔。
  - 「提出異議…」：選一檔，從它比價產生的自動事件裡選一筆、寫備註（必填，例如上手通知的內容）。異議不改事件；「異議」欄顯示「待確認：事件：備註」，直到解除。
  - 「解除異議…」：選一檔，選一筆還沒解除的異議解除（修好資料或程式、確認之後），記下解除的人與時間。

「9 出場清單」列出某一個收盤日出場的 KO、接股、到期還本、顧客贖回（[#171](https://github.com/TaylorYam/structured-product-workflow/issues/171)、[#188](https://github.com/TaylorYam/structured-product-workflow/issues/188)）：早上匯入昨日收盤價後，看昨天有哪些商品出場。
- 收盤日填 YYYY-MM-DD，空白是收盤價表最新的一天；按「重新整理」讀資料庫，讀到後把日期填回去，改日期再按一次就看那一天。回補股價或匯入歷史收盤價比價完成後，這一頁先帶入比到的那一天並顯示提示條，「1 每日匯入」出現「下一步：出場清單 →」，按了才切過來，也要按「重新整理」才讀。
- 列還有效（沒有被取代）、事件日是那一天的 KO、接股、到期還本、顧客贖回，一筆一列；來源不限：比價算出的、舊清單（以前清單更新的狀態）、人工登記的顧客贖回都列，和「8 進度」的存續狀態對得起來（#188）。沒有事件日的事件（例如部分舊清單的到期還本）不在任何一天。依事件、TDCC 排序。重點數字是 KO、接股、到期還本、顧客贖回四格，完成訊息寫出各來源的檔數；那天沒有時顯示「沒有出場的商品」。
- 欄位：TDCC、上手、商品、事件、事件日、標的（接股時是最差表現的標的）、來源（比價、舊清單、人工）、鎖住（已鎖住／未鎖住）、記錄時間（事件寫入的時間）。
- 「匯出 Excel…」：把畫面上的表寫成 Excel，預設檔名 `出場清單_<收盤日>.xlsx`，從上次匯出的資料夾開始；欄位同畫面。

### 核對條件

「1 每日匯入」或「2 起單資料」匯入完成後，自動替每檔**還沒鎖住**的商品算出核對需要、但起單資料沒有的資料，和上一次算的不同才寫進資料庫（[#88](https://github.com/TaylorYam/structured-product-workflow/issues/88)、[ADR 0012](docs/adr/0012-check-terms-calculation.md)）；已鎖住（核對通過）的商品不重算。更新時安裝器會自動套用尚未執行的 migration。

- **進場價、執行價、下限價、KO 價**（UL_1～UL_5 每個標的）：用取價日比 Strike date 晚的第一份股價檔，期初定價是收盤價取「最新收盤價」、開盤價取「最新開盤價」。執行價／下限價／KO 價 = 股價檔原值 × 執行價(%)／KI(%)／KO(%) ÷ 100，四個價格各自四捨五入（half-up）到小數第 4 位；KI 型態 NONE 時下限價空白。期初定價是 VWAP 時四個價格留空（由 TS 回填，#68），不算待確認。
- **股價檔對不對得上**：依 `config/exchange_holidays.toml` 確認 Strike date 是標的市場的交易日，而且和取價日之間沒有該市場的其他交易日（例如週五交易用週一的檔沒問題；漏匯一天就不行）。交易所碼不在假日表（目前有美國、日本、港股）或日期超出涵蓋範圍也是待確認。
- **分公司配置**：這檔的交易列（取消的列不在資料庫，PB 也算）同一分公司的金額加總，依出現先後，取代原本的配置；寄信草稿照舊讀它。
- **交叉比對**：交易明細和起單資料的幣別、交易日、UF（交易明細寫比例 0.0199，起單資料是百分點 1.99），交易列之間不一樣也算不一致。承作金額不比。
- **狀態**：完成／等股價（還沒有取價日比 Strike date 晚的股價檔）／等交易明細（交易明細還沒有這檔）／待確認（原因，例如「UL_2 AAA UW：股價檔（取價日 2026-10-16）沒有這個代碼」「UF不一致：起單資料 1.99、交易明細 0.0215（換算 2.15）」）。代碼找不到、沒有價格、股價衝突時只有那個標的的價格留空。股價或交易明細之後才到時，下一次匯入會自己補算。
- **缺資料**（[#114](https://github.com/TaylorYam/structured-product-workflow/issues/114)、[ADR 0016](docs/adr/0016-partial-product-terms.md)）：資料庫的商品條件可以先存一部分（之後在「7 人工維護」補），缺起單資料的必填欄時不算價格、不交叉比對，狀態是待確認，原因寫出缺哪幾欄（例如「缺 Strike (%)、Maturity date」）；分公司配置照樣由交易明細算。補齊後下一次重算照常。缺欄的商品不能核對、放行，也不會回填或鎖住；寄信草稿標待處理並寫出缺的欄。作業人員更新時由安裝器自動套用資料表版本 0012；開發環境請使用上面的手動遷移指令，既有資料不變。
- **放行差異**：交叉比對不一致、看過確定沒問題時，在「1 每日匯入」或「2 起單資料」的結果表點那一檔，按「放行差異…」。會記下 Windows 使用者名稱、時間與放行了哪些差異，然後重算那一檔；之後同樣的差異不再擋，資料改了、差異跟著變時要重新放行。股價、假日表的問題不能放行，要修正資料（例如補匯股價檔）。
- **風險等級**（[#238](https://github.com/TaylorYam/structured-product-workflow/issues/238)、[ADR 0023](docs/adr/0023-self-calculated-risk-level.md)）：同一次重算照承辦的 Generator 試算表公式算出 RR1～RR5，總分 = 0.4×保本率（FCN 固定 5）+ 0.2×年期 + 0.3×結構複雜度（標的種類、標的數量、波動度三項分數的平均再加提前贖回 1；波動度看各標的 200 日波動率的平均）+ 0.1×流動性（0.8×評等 + 0.2）；總分 <1.8 是 RR1、<2.6 RR2、<3.4 RR3、<4.2 RR4、其餘 RR5。波動率用取價日＝交易日那一份股價檔（沒有就用交易日以前最近一份）的「200日波動率」；評等用「發行機構評等…」裡保證機構（沒有就發行機構）在交易日的評等，三家取最好的。標的 UL_1 在 `config/risk_level.toml` 的指數清單上算指數，否則算個股（清單目前是空的）。缺資料算不出來時：交易日在 2026-10-30 以前填 RR4、狀態「回填」，之後的狀態「待算」，兩者都寫出缺什麼；待算的資料補齊後下一次匯入就會算出。已鎖住的商品只在還沒有風險等級時算一次（本功能上線前就鎖住的），之後不再改變（更正也不重算）。「2 起單資料」的風險等級欄顯示資料庫存的值，讀取時就會顯示，已鎖住的也顯示。指數清單可以寫 `SPX Index` 或 `SPX`（比對時去掉 Index、Equity 這類字尾）。結果存在 `workflow.risk_level`。說明書／投資人須知的 RR 核對與寄信草稿都用這個等級（[#239](https://github.com/TaylorYam/structured-product-workflow/issues/239)）：從資料庫產生的參考條件表多一欄「風險等級」（待算寫「待算」），全文風險等級、固定警語裡的 RR、投資人須知商品簡介的 RR 都和它比，不同判不一致，待算轉人工覆核；用沒有這欄的舊 Excel 參考條件表核對時照舊用審查標準的 RR4。核對後重算改了等級，寫回時當成條件已變、不回填（核對時的參考條件表沒有這欄則不算改了）。
- 結果存在 `workflow.check_terms`（狀態、原因、用的股價檔）、`workflow.underlying_price`（各標的的四個價格）與 `workflow.branch_allocation`；放行紀錄在 `workflow.cross_check_release`。#68 核對時讀這些表。重算失敗（例如假日表設定檔有問題）時匯入照樣保留，完成訊息寫出原因，排除後再匯入一次就會重算。

### TS/IIS batch preparation

Picks the Chinese term sheet and investor information sheet from TDCC-named product folders under the shared FCN directory, renames them to the checker's `<TDCC>_TS.pdf` and `<TDCC>_IIS.pdf`, and places them in a new batch folder. Product folders are read only.

**Operator setup (Windows)**: install official Python 3.11 or later (with Tcl/Tk), place the project in a folder you can write to, create the PostgreSQL database and daily account, and place `.env` in the install folder before double-clicking `setup_panel.cmd`. On the 3 準備 (prepare) tab:

1. Paste the TDCCs to check (newlines, spaces, commas, or ideographic commas; duplicates count once).
2. Check the root folder at the top of the window (product folders may be at any depth; press 變更… to change it), then choose the output location; both are remembered in local `.local/`.
3. Press Start. Each run creates `待核對_<timestamp>` in the output location and refuses an existing folder.
4. Identification uses page-one content: a 中文產品說明書 or 中文投資人須知 title near the top; the term sheet's first page must contain the folder TDCC, and an investor sheet's 12-digit code must match when present. File names are hints only.
5. Issuer PDFs take precedence. Only when a document type has no PDF (for example MS and BNP provide Word only) are the folder's Word files (`.docx`, `.doc`) copied to a temporary area and converted with Microsoft Word before identification ([ADR 0002](docs/adr/0002-word-to-pdf-with-microsoft-word.md)). Original Word files stay untouched; a failed or timed-out conversion (for example a Word dialog) skips that product. The MS term sheet cover always leaves 受託機構商品代號 (trustee product code) blank, so the TDCC is filled into the temporary copy before conversion (existing values are left alone) and nobody edits the Word by hand; the original Word in the product folder stays blank, while the returned and mailed PDF is the filled one; the preparation list's reason column says 已補受託機構商品代號 ([#56](https://github.com/TaylorYam/structured-product-workflow/issues/56)).
6. If either document is missing or has multiple candidates, the whole product is skipped with the reason and candidate names.
   **Rechecking revised issuer documents**: `_待確認` files returned last time are never candidates and only identify which version failed (full-text comparison); identical copies count once. A newly sent version is picked, replacing even the previously returned standard-name version (also when the revision reuses the old file name and overwrites the old original: with differing contents the issuer-named version wins and content found only under the standard name is treated as the previous return); until the issuer sends one, the previously failed version is reused (the reason says so, and also lists new files that could not be used because of a cover-code mismatch or failed conversion), so the same version can be rechecked after fixing the reference workbook or checker rules; a new error workbook is written only when the errors differ from the latest one in the folder. The preparation list's reason column names the excluded versions. For Word-only issuers such as MS and BNP, only the failed document is replaced; if both changed, move the old standard-name file into a subfolder first. When the failed version was a PDF, the revision must also include a PDF to be picked (for example, ask JPM, which sends both PDF and Word, for a PDF when the revision is Word only).
7. `準備清單.xlsx` in the batch folder records each document's source, whether it was converted from Word, output name, SHA-256, status, and reason. Optionally press 打開批次資料夾 to look at the batch folder; press 下一步：核對 → to switch to 4 核對 (check), where the prepared PDFs are already filled in; the 條件來源 defaults to the database, so load the preview directly (with Excel, choose the reference workbook first).

Without connection settings, or when the login is cancelled, preparation runs as usual without records; when the database cannot be reached or the write fails, the preparation list is still produced and the completion message says why. Operator installs/updates apply schema version 0015 automatically.

After checking and saving the checker result workbook, press 下一步：放回 → to switch to the 5 放回 (return) tab:

1. The batch folder and the result workbook just saved on 4 核對 are already filled in (change them with 選擇… or the hint bar's 改選…).
2. Press Return. Products whose `TS/IIS完成檢核` is `V` on the result workbook's 回填後 sheet (both documents passed or manually released) are returned under standard names. A document listed on the error-list sheet is returned with `_待確認` appended (for example `<TDCC>_TS_待確認.pdf`), while the product's passing document keeps its standard name and the reason column carries the error messages; a `<TDCC>_錯誤訊息_<timestamp>.xlsx` workbook (one error per row with the PDF page numbers, which refer to the returned `_待確認` file) is also written to the product folder so operators can see the problems there. It is not written again when the pending files are already in place. Products absent from the result workbook (not yet checked) are not returned.
3. Batch PDFs are re-hashed and must match the preparation list. When a product folder already has a same-named file, identical content (same bytes, or the same full text such as a PDF re-converted from the same Word file) counts as already there (for example UBS issuing standard names); different content is never overwritten and the whole product is not returned, leaving the decision to the operator.
4. Files are copied only and the batch folder is kept; results go to `放回清單_<timestamp>.xlsx` in the batch folder, which also lists prepared products not yet checked as not returned. After fixing and rechecking failed products, returning again marks already returned files as already there; when a standard name is returned, old `_待確認` files and error workbooks are never deleted automatically and the list reminds you to remove them after review.
5. **Step records at the same time** ([#151](https://github.com/TaylorYam/structured-product-workflow/issues/151), [ADR 0019](docs/adr/0019-progress-step-records-and-lifecycle-events.md)): every product returned or already there gets a 已放回 record (including products returned with a `_待確認` file, whose result says 含待確認 and both documents' statuses); products not returned get none; connection settings and failures are handled as in 3 準備.

4. **Terms from the database** ([#68](https://github.com/TaylorYam/structured-product-workflow/issues/68), [ADR 0013](docs/adr/0013-check-from-database.md)): choose 資料庫 as 條件來源 and no reference workbook is needed. Loading the preview generates a same-format reference workbook from the database for the TDCCs in the PDF file names (kept in the install folder's `runtime/資料庫參考條件表/`); checking, manual release, the result workbook, and the report bundle then work exactly as with Excel. Excel was the default until [#108](https://github.com/TaylorYam/structured-product-workflow/issues/108); the database is now the default, and the 參考條件表 row is hidden while it is chosen.
   - A product missing from the database, with blank required terms ([#114](https://github.com/TaylorYam/structured-product-workflow/issues/114)), whose check terms are not 完成 (等股價, 等交易明細, 待確認; see "Check terms" below), or an old locked 清單更新 product: that document is not checked, needs review with the reason, and cannot be released; the rest of the batch proceeds.
   - After "儲存核對結果…" writes the result workbook, the database is updated: products whose term sheet and investor sheet both passed or were released get their ISIN, issue date, and observation dates (plus each underlying's prices for VWAP) backfilled, a released term sheet's denomination becomes the TS value, and the product is **locked** (order-sheet imports can no longer overwrite it). A product whose terms changed after checking (for example a re-imported order sheet) is neither backfilled nor locked; reload the preview and check again. Each document's latest result and every changed value's old value stay in the database. Locked products can be checked again but are not backfilled again.
   - If the write-back fails (for example a dropped connection) the result workbook is kept, the window gives the reason, and "重新寫回資料庫" retries after the fix.
   - Command line: `fcn-batch --database <PDFs…> --out <output folder>` (connection settings from `.env`, asking for a missing password; the generated reference workbook goes to the output folder).
   - On operator installations, rerunning `setup_panel.cmd` applies pending schema migrations using the install folder's `.env`; during development, run `spw-db-migrate --env-file .env --admin-user postgres`.

Rules, templates, support scope, the reference workbook format, and the checker's ADRs are in [docs/checker/](docs/checker/README.md) (Chinese only; issue numbers there refer to the original repository). For a new issuer or template version, follow the [issuer onboarding flow](docs/checker/issuer-onboarding.md).

### Daily import (minimal FCN database)

Imports each day's FCN trade rows and daily prices into PostgreSQL ([#87](https://github.com/TaylorYam/structured-product-workflow/issues/87), [ADR 0008](docs/adr/0008-daily-prices-denomination-and-order-dates.md)); product terms are imported after confirmation on 2 起單資料; the mailbox is maintained directly in the database ([ADR 0004](docs/adr/0004-mailbox-maintained-in-database.md), [#35](https://github.com/TaylorYam/structured-product-workflow/issues/35)) ([#32](https://github.com/TaylorYam/structured-product-workflow/issues/32), [ADR 0003](docs/adr/0003-minimal-fcn-database.md)). Mail drafts will read only this database.

**First-time setup (once per computer)**:
1. Install PostgreSQL and create the database and the daily account (`scripts/provision_postgres_dev.py` can help).
2. Create `.env` in the install folder (the repository root during development) with `PGHOST`, `PGPORT`, `PGDATABASE`, and `PGUSER`; `PGPASSWORD` is optional and is asked for at import time. `.env` never enters Git.
3. On operator installations, `setup_panel.cmd` creates the tables with an account that can create schemas and grants read/write to `PGUSER`. In development or when running a manual migration, explicitly use the repository `.env`:

```bash
spw-db-migrate --env-file .env --admin-user postgres
```

After an operator code update, rerun `setup_panel.cmd` to apply pending versions; in development, rerun the command above. When moving to another computer (for example from the laptop to the company computer), do not copy the database: create the database, account, and `.env`, run setup, then re-import the daily updates.

**Daily**:
1. Open the daily update (template `PostgreSQL每日更新.xlsx`, kept only in the private samples repository): paste yesterday's trade rows whole into `交易明細` (same columns as the trade-list monthly sheets; do not change the header row); `BBG_Data` pulls prices per the template (C1 is the price date, and the values are the previous trading day's). The old `清單更新` sheet is retired and is ignored if present.
2. In the window, open "1 每日匯入", choose the daily update, and click "匯入".
3. Import the MarketData CSV every day ([#153](https://github.com/TaylorYam/structured-product-workflow/issues/153), [ADR 0020](docs/adr/0020-close-prices-and-observation-rules.md)): under "回補股價", choose the Bloomberg export `MarketData_YYYYMMDD.csv` for the previous trading day and click "回補股價". Besides the prices (see "Backfilling earlier days" below), this stores that day's closes in the close-price table for observation; if it is forgotten, observation stops at "等股價".
4. Review the results:
   - "新增交易": written. "已存在": imported before; nothing written this time.
   - "內容不同（未覆蓋）": the trade rows differ from the database, which keeps the first version. If the database value is wrong, fix it on "7 人工維護" (see "Manual maintenance" below); once it matches the workbook, a re-import shows "已存在".
   - "擋下": a row is missing values or uses an unrecognized form; fix the workbook and re-import.
   - "股價衝突": a code appears on several `BBG_Data` rows with different values; its prices are not stored and cannot be used for pricing. Duplicate rows with identical values count once.
   - "股價不是數字": a price cell is not a number (for example `#N/A`) and is stored blank.
   - "交易已取消": the trade-row 備註, after trimming and case-folding, is `Cancel`, or it contains `取消`; the row is not imported into the database.
   - "名字對不到信箱": an FC name is missing from `mailbox.person` (case is ignored); for spelling variants add an alias to `mailbox.alias`.
   - "信箱尚未建立": `mailbox.person` is empty, so names cannot be matched.
   - The completion message also gives the price date and count; re-importing the same price date replaces that whole day (every import is recorded).
   - "核對條件：…": unlocked products are recalculated after the import (see "Check terms" below); products that changed or are not done are listed.
5. After the import, the trade sheet's FCN TDCCs are already filled into "2 起單資料" (the completion message says how many); click "下一步：起單資料 →" to go on and read the order sheet ([#90](https://github.com/TaylorYam/structured-product-workflow/issues/90)). Products already in the database are included; nothing is filled in when the trade sheet has no FCN or the whole file is rejected.

**Backfilling earlier days** (after Taiwan holidays or leave, [#112](https://github.com/TaylorYam/structured-product-workflow/issues/112), [ADR 0015](docs/adr/0015-price-csv-backfill.md)): BBG_Data only fetches the latest prices, so trade rows and prices are imported separately.
1. Trade rows: use the daily update as usual, tick "只匯交易明細", and click "匯入"; BBG_Data is not read and prices are untouched.
2. Prices: choose the Bloomberg export `MarketData_YYYYMMDD.csv` under "回補股價" (one at a time) and click "回補股價". The CSV price date is the closing day and is stored as **the next day** (10/16 close → price date 10/17), the same as a BBG_Data pull the next morning; that day's existing prices are replaced whole. Headers must match exactly; the whole file is rejected when a price date is not a date, spans more than one day, or there are no codes. There is no previous close, and currency and USD market cap are not stored. Check terms are recalculated afterwards, and problems go to `每日匯入錯誤.xlsx` beside the CSV.

**Close prices** (for observation, [#153](https://github.com/TaylorYam/structured-product-workflow/issues/153), [ADR 0020](docs/adr/0020-close-prices-and-observation-rules.md)): one row per actual closing day and code, separate from the price-date prices above; BBG_Data never writes closes (its date is ambiguous).
- Codes drop the trailing Bloomberg class word (`AAA UW Equity` → `AAA UW`, `USDJPY Curncy` → `USDJPY`) and otherwise stay character for character, matching the underlying codes in the product terms.
- Only trading days of the code's market are stored: weekends and closed days in the exchange holiday calendar (`config/exchange_holidays.toml`, covering the US, Japan, and Hong Kong) are skipped, so the previous day's price a CSV carries on a closed day is ignored. Codes whose exchange is not in the calendar are stored, and observation flags them for confirmation later; when the exchange is in the calendar but the date is outside its coverage (for example historical closes before the calendar's 2022-07-28 start), the day cannot be confirmed as a trading day, so the close is not stored but listed; add those years to the calendar and import again.
- When the holiday calendar cannot be read, the backfill still imports the prices but stores no closes this time (the completion message says so); fix the calendar and import the same CSV again.
- Re-importing the same (closing day, code) replaces the row; when the value changed, the old value is kept in `workflow.close_price_change`.
- When one code has different values after dropping the class word (for example `AAA UW` and `AAA UW Equity`), or a code has a price conflict, its close is not stored.

**Historical close import** (one-off, "匯入歷史收盤價…" on the 維護 menu): choose an HP-format workbook (first sheet; closing days across row 3 from column E, one instrument per row from row 4, column C holding the Bloomberg code with its class word). Progress and results show on "1 每日匯入".
- The whole file is read and checked before anything is written: it is rejected when row 3 has a non-date cell, a closing day repeats, there are no closing days, or there are no codes; it is also rejected when the holiday calendar cannot be read.
- Error values (`#N/A N/A`, `#N/A Requesting Data...`, `#N/A Invalid Security`, `-`, garbled text, broken formulas), blanks, and non-positive cells all mean no price. Values on closed days are not stored; a repeated code with different values on the same day is not stored.
- Problems are grouped by code and reason (first day, last day, cell count) into `歷史收盤價錯誤_<timestamp>.xlsx` beside the source file; `#N/A N/A` is listed only on confirmed trading days. Nothing is written when there are no problems. `#N/A Requesting Data...` means the fetch did not finish; fetch again and re-import.
- The completion message gives the date range, the code count, the number of cells without a price (closed days excluded), and where the error list is.

**Observation** ([#155](https://github.com/TaylorYam/structured-product-workflow/issues/155), [ADR 0020](docs/adr/0020-close-prices-and-observation-rules.md)): runs automatically after the price backfill and the historical close import, and from "重新比價全部" on the 維護 menu (no import; it uses the closes already stored). Every product whose check terms are 完成 (locked or not) is observed day by day up to the latest day in the close table; the KO, 接股, and 到期還本 found are written as lifecycle events, and each product gets one observation status in `workflow.pricing_status` (在庫／等股價／待確認／已出場, reason, observed-through date, locked or not); both are written only when they change.
- KO: close ≥ KO price. Non-memory needs every underlying on the same observation day; memory remembers each underlying that reached it on any observation day and knocks out once all have. Daily KO types observe every day from the first autocall date to the final valuation date on which all underlying markets are open; period-end types look only at the stored autocall dates; products whose Non-Call equals the tenor are not observed for KO.
- KI: at-maturity (EKI) looks only at the final valuation date, close < KI price; daily (AKI) looks at every trading day of the underlying's market after the Strike date; periodic (MKI) is not observed (autocall dates 1-12 hold only the KO periods); KO is still observed and decides the status, the KI column shows "MKI (manual)", and a final valuation date without KO is 待確認 for a person to decide delivery or redemption ([#196](https://github.com/TaylorYam/structured-product-workflow/issues/196), [ADR 0022](docs/adr/0022-pricing-status-is-ko-only.md)).
- Maturity (final valuation date without KO): with no KI, or with KI touched, when the worst performer (lowest final close ÷ initial price) closes below its strike → 接股 (recording that underlying); otherwise 到期還本. The event date is the observation day of the trigger or decision.
- When a price needed on a trading day of an underlying's market is missing from the close table, the product stops on that day (observed through the day before) with status 等股價 naming the underlying and date; once the price arrives the next run carries on. An exchange not in the holiday calendar, a date outside its coverage, a code with no closes at all once it is needed, an autocall date on a closed day, or missing prices or autocall dates in the terms → 待確認 with the reason.
- Exited products are no longer observed ([#169](https://github.com/TaylorYam/structured-product-workflow/issues/169), [ADR 0021](docs/adr/0021-stop-observing-exited-products.md)): a product with a lifecycle event (KO, 接股, or 到期還本 from observation, a recorded 顧客贖回, or a 舊清單 event) is 已出場 with the event and its date as the reason, keeps its previous compared-through date, and its events are not recalculated; close prices are assumed not to be corrected later. Products whose check terms are no longer 完成 stay 已出場 when they have exited and otherwise become 待確認. When the terms of an exited product are changed on "7 人工維護", the save result reminds that the events do not follow; raise an objection on "8 進度" when they differ from the issuer's notice.
- A product still in its non-call period (before the first autocall date) and on book shows the reason "Non-call period（第一個比價日 YYYY-MM-DD）"; the status, observed-through day, and reason cover KO only: the observed-through day is blank before the first autocall date and for products that never observe KO; a daily-observed KI (AKI) is still checked every day from the day after the strike date, and a missing price it needs is still 等股價 with "（每日觀察 KI）" after the reason. KI has its own column on the progress page in English codes: No KI, EKI, AKI, MKI (manual), or `AKI hit date underlying` (first touch); exited products without a stored KI show the KI type ([#198](https://github.com/TaylorYam/structured-product-workflow/issues/198), [#196](https://github.com/TaylorYam/structured-product-workflow/issues/196), [ADR 0022](docs/adr/0022-pricing-status-is-ko-only.md)). A product whose non-call equals its tenor shows "還沒到最終比價日（YYYY-MM-DD）" until the final valuation date ([#194](https://github.com/TaylorYam/structured-product-workflow/issues/194)).
- The completion message gives the observed-through day and the count per status; the result table lists the lifecycle events that changed and the products not done (等股價, 待確認), marking unlocked ones 未鎖住. When observation fails the import is kept and the message gives the reason.

**Old-product prices and autocall dates** (one-off, "匯入舊商品的價格與比價日…" on the 維護 menu, [#154](https://github.com/TaylorYam/structured-product-workflow/issues/154)): locked products created by the old 清單更新 have no per-underlying prices or autocall dates, so they cannot be observed. Choose a reference-workbook-format Excel (for example the backfilled inventory master); progress and results show on "1 每日匯入", and observation runs afterwards as usual:
- Only locked products that still lack underlying prices or autocall dates are handled, and only the missing part is filled: the initial, strike, KI, and KO prices of UL_1 to UL_5 (codes come from the database and the sheet's codes must match, ignoring case, spaces, and a trailing Equity) and 比價日 1 to 12 (the empty-value marker is stored as blank); no other column is touched. A product without check terms also gets a 完成 check-terms row naming the source file, so observation picks it up; existing check terms are left alone, and when they are not 完成 the result says so (observation will skip the product until they are fixed).
- The sheet's 庫存狀態: "已於 Y/M/D KO" becomes a KO event (event date that day) and "到期還本" a 到期還本 event (event date is the product's final valuation date in the database, blank when it has none; [#189](https://github.com/TaylorYam/structured-product-workflow/issues/189)), with source 舊清單; an existing event of the same kind is not duplicated (a different KO date is reported for review), and a product with an event of another kind is not imported. Without a 庫存狀態 column only prices and dates are filled.
- A product missing from the sheet or the database, not locked, listed on two rows, with a code different from the database, a price that is not a number, a blank initial, strike, or KO price, or an autocall date that is not a date is not imported and the reason is shown, while the rest go ahead; those products are also written to `舊商品補資料錯誤_<time>.xlsx` beside the source file. A missing required column rejects the whole file.
- The whole import is one transaction; re-importing the same file reports 已存在 and rewrites nothing.

Only FCN is imported; other products are skipped and counted. Trade rows whose 備註 is `Cancel` or contains `取消` are not imported. Re-importing the same file writes no new trades, and any error leaves no partial data. All import problems are rebuilt into one `每日匯入錯誤.xlsx` beside the source workbook, including prior import history, so September and October appear in the same workbook. The note field is authoritative for cancellation; Excel fill colors are not inspected. Prices are keyed by price date and code; codes are only trimmed, never re-cased or mapped to another exchange; the whole file is rejected when `BBG_Data` C1 is not a date or the row-2 headers differ. The daily import writes no product terms, does no branch reconciliation, and never changes the mailbox; branch allocations are derived from the trade rows when check terms are recalculated after the import (#88). Products written by 清單更新 before #87 are kept, and unlocked ones are recalculated too.

**Mailbox maintenance** ([#158](https://github.com/TaylorYam/structured-product-workflow/issues/158)): in the window's 「維護」 menu choose 「信箱維護…」 to open a separate window, with people on the left (name, email, unit, fixed CC, aliases) and aliases on the right (alias → person). Use 「新增人員…」 or 「新增別名…」, or select a row and use 「修改…」 or 「刪除…」 (double-click also edits); pressing 確定 saves to `mailbox.person` / `mailbox.alias` and records who, when, and the before and after values in `mailbox.change_log`. Names must be unique ignoring case, and invalid email formats, duplicate aliases (ignoring case), and aliases pointing to unknown people are rejected with the reason shown on screen and nothing half-saved. Renaming a person updates their aliases; deleting a person also deletes their aliases (listed in the confirmation first). A row someone else changed after you opened the window is not overwritten; press 「重新整理」 and edit again. The window warns when no one is a fixed CC, because mail drafts would stop.

**Issuer credit ratings** ([#237](https://github.com/TaylorYam/structured-product-workflow/issues/237)): in the 「維護」 menu choose 「發行機構評等…」 to open a separate window listing each issuer's issuing entity and guarantor on the left (issuer, role, name, and the current S&P / Moody's / Fitch ratings with their effective date); select one to see its rating history on the right (newest first). When a rating changes, select the entity, press 「新增評等…」, and enter the effective date and the three ratings (leave an agency blank when it has no rating; at least one is required); the effective date must be later than the latest one. Only the latest rating can be edited or deleted (「修改最新一筆…」, 「刪除最新一筆…」), and every entity keeps at least one. For a new issuer use 「新增機構…」 (a blank effective date means no start date). Ratings are stored in `workflow.rated_entity` and `workflow.credit_rating`, and each save records who, when, and the before and after values in `workflow.credit_rating_log`; wrong formats (such as A+ for Moody's) are rejected with the reason shown. The rating used for a trade date is the latest one effective on or before it; the first ratings (14 issuers, 18 entities, taken from the 580 term sheets and investor information statements of 2026-09 to 10) show 「最初」 as their effective date and apply to any trade date. When checking ([#240](https://github.com/TaylorYam/structured-product-workflow/issues/240)), the reference workbook generated from the database carries the ratings in effect on the trade date, and the ratings stated in the term sheets and investor information statements of all 14 issuers must equal them: the issuing-entity ratings of BARC ([#243](https://github.com/TaylorYam/structured-product-workflow/issues/243)), HSBC, MS, DBS, Natixis, and UBS, as well as both the issuing-entity and guarantor ratings of Citi, GS, BNP, and BBVA ([#242](https://github.com/TaylorYam/structured-product-workflow/issues/242)) and the guarantor ratings of CA, JPM, Nomura, and SG ([#241](https://github.com/TaylorYam/structured-product-workflow/issues/241); their issuing entities are unrated vehicles, so the issuer rating is not checked when the document states it is unrated and needs review otherwise) (agencies a document does not state are not compared; an entity missing from the rating table needs review; rules in `docs/checker/rules/shared-check-rules.md` §10). For issuers with rating checks (all 14 now; a new issuer may go live before its rating check is done), a rating changed after checking counts as changed terms, so write-back skips that product.

Fallback: SQL directly in the database still works (with an account that has write access); the lowercase matching keys are generated by the database and the same checks apply, but no `mailbox.change_log` entry is written.

If the same PostgreSQL database already has another system's `public.mailbox` (for example, with `user_name`, `email`, and `unit` columns), this project does not read or modify it. `public.mailbox` is a table; this project uses the separate `mailbox.person` and `mailbox.alias` schema/table set created by its migrations, so both can coexist. To seed the project mailbox from an existing list, review the data first and have an administrator run a one-time SQL statement explicitly; there is no automatic synchronization, and `fixed_cc` must be confirmed separately:

```sql
INSERT INTO mailbox.person (name, email, unit, fixed_cc)
SELECT user_name, email, unit, false
FROM public.mailbox
ON CONFLICT (name_key) DO NOTHING;
```

```sql
-- Add a person (fixed_cc = true marks a fixed mail CC)
INSERT INTO mailbox.person (name, email, unit, fixed_cc) VALUES ('Amy', 'amy@example.com', 'FC', false);
-- Add an alias when the trade list spells the name differently
INSERT INTO mailbox.alias (alias, person_name) VALUES ('Amie', 'Amy');
-- Update or delete
UPDATE mailbox.person SET email = 'amy.new@example.com' WHERE name = 'Amy';
DELETE FROM mailbox.person WHERE name = 'Amy';  -- their aliases are deleted too
```

### Mail drafts

Creates TS/IIS emails to the FCs handling each checked FCN in **your own classic Outlook Drafts folder** ([#29](https://github.com/TaylorYam/structured-product-workflow/issues/29)). **It only creates drafts and never sends**; review each one in Outlook and send it yourself. All data comes from the database, so run the daily import first.

1. In the window, open "6 寄信草稿" and paste the checked TDCCs (same separators as preparation).
2. Choose the result-list location (the root folder is the one at the top of the window, as in preparation), then click "建立草稿". The window first shows the latest daily import (time, run number, file name) and creates drafts only after you confirm.
3. A draft is created only when all of these hold; otherwise the product is marked "待處理" with reasons:
   - the database has the product's terms (no blank required field used in the mail, [#114](https://github.com/TaylorYam/structured-product-workflow/issues/114); a blank initial pricing stays blank in the mail) and trade rows;
   - the product folder holds `<TDCC>_TS.pdf` and `<TDCC>_IIS.pdf` (return-to-folders only writes standard names for checked documents; `_待確認` files do not count);
   - every FC on the trade rows matches the mailbox.
4. Mail: one per product; recipients are the FCs (PB skipped; PB-only products are "不需寄送"), CC is everyone with `fixed_cc` in the mailbox; subject `[中文TS/IIS] [FCN] - <TDCC>`; the body uses the Excel template configured by `.env` `SPW_MAIL_TEMPLATE`, fills it, and pastes editable tables into Outlook; both PDFs are attached.
   The risk level is the self-calculated one ([#239](https://github.com/TaylorYam/structured-product-workflow/issues/239); backfilled products show RR4); when it is pending or not calculated yet the draft says 待確認 and is still created, and the result list and the window mark that product with the reason, so fill it in before sending.
   Table content is centered; English uses Calibri and Chinese uses Microsoft JhengHei; table headers are limited to two lines. Fixed CCs are ordered MAX, BOB, then PM, followed by other people.
5. The result list `寄信草稿清單_<timestamp>.xlsx` records each product's status, recipients, CCs, and reasons; its "資料來源" sheet records which daily import was used (time, run number, file name, SHA-256) and any folders that could not be read.
6. **Step records at the same time** ([#151](https://github.com/TaylorYam/structured-product-workflow/issues/151), [ADR 0019](docs/adr/0019-progress-step-records-and-lifecycle-events.md)): every product with a draft gets a 草稿已建立 record (who, when, the result list); 待處理, 不需寄送, and 建立失敗 products get none. When the write fails, the drafts and result list stay as they are and the completion message says why.

Non-FCN products skipped by the daily import are marked "不支援的商品類型". Running a product again creates another draft; delete duplicates yourself. An error on one product (for example Outlook not responding or bad data) marks only that product "建立失敗"; the others continue. Product folders are read only. After an operator code update, rerun `setup_panel.cmd` to apply pending schema versions; in development, use the manual migration command above.

### Order sheet (起單資料)

Reads the operators' daily order sheet `起單建檔_<date>.xlsm`; operators confirm and edit each product in the window, then import it into the database ([#97](https://github.com/TaylorYam/structured-product-workflow/issues/97), [ADR 0010](docs/adr/0010-order-terms-from-daily-order-sheet.md); the confirmation screen is from [#86](https://github.com/TaylorYam/structured-product-workflow/issues/86) and [ADR 0009](docs/adr/0009-confirm-order-terms-in-window.md)). `(Order)` emails are no longer read, and no Excel is exported.

1. In the window, open "2 起單資料", paste TDCCs (same separators as preparation; right after a daily import the trade sheet's FCN TDCCs are already filled in, and 改選… on the hint bar clears them so you can paste your own), click 選擇… next to 起單建檔 to pick the day's file (the first time it opens `G:\Bond Data\PM事項\0.常用工具\ELN每日起單建檔`, later the folder last used), and click "讀取". This page does not use the root folder.
2. Only the chosen file is read, and it is never changed. The sheet has one worksheet; the row among the first few that contains `TDCC` is the header (currently row 2 from column B), and columns match by header text, ignoring case and position. Columns read: Product, Currency, Guaranteed Periods (m), BBG Code 1–5, Strike (%), KO Type, KO Barrier (%), Coupon p.a. (%), `UF (%)` (older header `Upfront / NotePrice (%)`), Tenor (m), Barrier Type, KI Barrier (%), the four dates, and 期初價格. Other columns (No., Observation Frequency, OTC, Funding Spread, Effective Date Offset, 起單FC) have no database field and are not read.
3. The `UF (%)` column holds the price (for example 97.14) and is shown as Upfront / NotePrice (%); the database gets UF = 100 − price.
   Strike date (the initial pricing date, [#101](https://github.com/TaylorYam/structured-product-workflow/issues/101), [ADR 0011](docs/adr/0011-strike-date.md)) is not a sheet column: when 期初價格 says 明日開盤價 (next day's open), 期初價格 becomes 開盤價 and Strike date is the underlyings' next business day after the trade date (from `config/exchange_holidays.toml`; a Friday trade gives Monday, and holidays push it further); otherwise Strike date equals Trade date. When the holiday calendar cannot tell (an exchange not in the calendar, or a date outside its range) Strike date stays blank and red for the operator (never filled from the database); Strike date may not be earlier than Trade date. Editing Trade date on screen moves a Strike date that equalled it; a 明日開盤價 Strike date stays put.
4. Rule-based, never guessing:
   - KO Type must be Daily, Daily Memory, Period End, or Period End Memory; Barrier Type NONE, EKI, or AKI; 期初價格 開盤價, 收盤價, or VWAP; case is ignored (`DAILY MEMORY` and `None` are accepted).
   - Unknown values (for example `MKI`, a number as KO Type, or 期初價格 written as 待確認), non-numbers in number columns, and non-dates in date columns leave the cell blank and red with the value read, for the operator to fix on screen.
   - The issuer comes from the TDCC's first three digits in `config/issuer_prefixes.toml`; an unknown prefix blocks the import.
   - A TDCC with several rows: identical rows are used; differing fields stay blank with each row's value shown and must be filled before importing (if blank is right, fix the sheet and read again).
   - A pasted TDCC missing from the file is 找不到; one that is not 12 digits is 待確認.
   - A file with several worksheets (such as the master `ELN每日起單建檔.xlsm`), no header, missing columns, or a duplicated column stops the whole batch with a reason.
5. After reading, the batch is listed below on the left (problems first) with an editor on the right:
   - Status: "待確認" means a field blocks the import (a required blank, a bad format, and so on); "請確認" means reading the sheet raised a reminder but the product can be imported; "可匯入"; "已鎖住" means the check passed or the product was already in the database at migration 0006, so it cannot be edited or imported (use "7 人工維護"; see "Manual maintenance" below). Products not found still show their reason.
   - Selecting a product lists the fields above on the right. Light red marks a field that blocks the import or had a reading problem, with the reason underneath; light yellow marks a value that differs from the database, showing the database value with a "用資料庫的值" button to restore it. KO Type, Barrier Type, and initial pricing use drop-downs, and dates are written `2026-10-21`; a field is checked when you leave it or press Enter, and a mistyped one keeps your text and turns red; that product is skipped on import while the rest proceed.
   - With connection settings in `.env` the database is consulted (a missing password is asked once before reading): for products already in the database and not locked (including ones 清單更新 created), fields blank in the sheet take the database value (except fields where duplicate rows differ). Without settings you can still read, with nothing filled from the database; a product read without the database never overwrites one already in it on import (read again first).
6. When done, click "匯入資料庫": products passing the checks are written to the database (denomination from the currency default; final valuation and maturity dates required; re-imports before the check passes overwrite with a record of the sheet file and row numbers and of manual edits against the sheet; blank fields never wipe database values you did not see), and the status column shows 新增/覆蓋/沒有變/不匯入/已鎖住, with the recalculated status in the 核對條件 column and the RR calculated alongside it in the 風險等級 column (see "Risk level" under "Check terms" below); select a product and click 「風險等級明細…」 for the breakdown. The order amount comes from the trade rows and is not entered here. Migration 0008 backfills existing products' Strike date from the trade date; setup applies pending migrations automatically on operator installs/updates (use the manual migration command above during development). Reading again, receiving new TDCCs, or closing the window with edits not yet imported asks first; the editor is locked while work is running.
7. Changing terms after locking now happens on "7 人工維護" (see "Manual maintenance" below); this page's "更正商品條件…" button is gone.

### Manual maintenance (人工維護)

Find products that still lack data, and fill in or change product terms ([#115](https://github.com/TaylorYam/structured-product-workflow/issues/115), [ADR 0017](docs/adr/0017-manual-maintenance-tab.md)) and trade rows ([#116](https://github.com/TaylorYam/structured-product-workflow/issues/116), [ADR 0018](docs/adr/0018-maintenance-trade-rows.md)) in the database by hand. Corrections of locked products ([#55](https://github.com/TaylorYam/structured-product-workflow/issues/55), [ADR 0014](docs/adr/0014-term-correction.md)) are made here too.

1. In the window, open "7 人工維護" and click "檢查": it lists unlocked products missing order-sheet required fields, plus TDCCs in the trade rows with no product terms in the database yet (status "只有交易明細", trade rows only), sorted by TDCC; the figures above give how many lack data and how many of those are trade-only. The table shows issuer, status, and the required fields cell by cell, with missing cells in light red; scroll sideways when the columns do not fit, with the TDCC column fixed on the left. Locked products are not listed (they are complete before locking).
2. Click a product to open it, or type any TDCC in the TDCC box and click "打開" (including locked and complete products; a TDCC in neither the trade rows nor the database cannot be opened). The editor on the right is the same as on "2 起單資料", with a note above it on how this product is saved. Changed fields (including cleared or newly filled ones) turn yellow showing the database value, with a button to restore it.
   - Unlocked: the database's current values are shown. Required fields may stay blank for now (light red, noted "缺，可以先存、之後再補"), except the product type; bad formats and inconsistent fields block the save under the order-sheet import rules, and KI Barrier (%) is still required with a KI barrier type (when unsure, leave Barrier Type blank too). The issuer cannot change; a changed currency switches the denomination to the new currency's default.
   - Trade rows only: starts blank with product type FCN, the issuer from the issuer prefix map (an unknown prefix blocks the save), and the denomination from the currency default. Saving creates the product terms with source 人工維護; a later order-sheet import overwrites them as usual.
   - Locked: the correction rules apply: no blanks, Issue date is backfilled from the TS and cannot change, the issuer cannot change, and a changed currency switches the denomination to the new currency's default. After saving the product stays locked (re-imports still do not overwrite it) and check results are untouched; products with check terms have their prices and cross-check recalculated when underlyings, percentages, Strike date, initial pricing, currency, trade date, UF, or similar fields change (VWAP keeps the TS-backfilled prices and recalculates only those whose percentage changed; positions with a new underlying are blank and marked 待確認), while changing only the coupon, maturity date, and the like does not recalculate.
   - Trade rows: the product's trade rows are listed under the product terms in database row order ("第 n 列"), with the daily import's columns; trade-only products show them too. Only values change: rows cannot be added or deleted, and 備註 cannot become Cancel or 取消. Typed text is read with the daily import's rules; 交易日期, 幣別, 金額, FC/PB, and 分公司 are required, and blanks or bad formats turn red and block the save; changed cells likewise turn yellow with a button to restore them. Unchanged cells keep their database values and never block the save. A changed FC name is matched against the mailbox with the daily import's rules; an unmatched name gets a red warning (mail drafts will not find that FC), but the save is allowed.
3. Click "存檔" (the reason is optional): product terms and trade rows are saved together. Unlocked products are written to the database and their check terms recalculated (staying 待確認 while fields are blank; trade-only products without product terms are not recalculated), and nothing is written if the recalculation fails; for a locked product whose trade rows alone changed, check terms are recalculated only when 交易日期, 幣別, 金額, 分公司, or UF changes, and the product stays locked with check results untouched; the completion message lists what changed, the recalculated status, and any FC names not in the mailbox, and the check table updates (a product now complete drops off). After saving, the editor shows the values as stored, so you can keep editing and save again.
4. Each save writes one `workflow.term_correction` row: values before and after (including changed prices), the previous product columns (blank for a new product), the Windows user name, the time, and the reason, with `locked` recording whether the product was locked. Nothing is written when nothing changed, or when after opening the product changed in the database, became locked (check passed), or got product terms from someone else; click "重新載入" (reload) first. Changed trade rows get their own `workflow.trade_row_correction` row: the changed cells (row, column, before and after), the product's trade rows before the save, the user, the time, and the reason, plus the recalculated prices that changed when only a locked product's trade rows changed. Nothing is written either when the product's trade rows changed after opening (for example a re-import added a row). Opening another product, reloading, or closing the window with unsaved edits asks first. Later daily imports still do not overwrite the database. Rerun `setup_panel.cmd` after updating and the installer applies schema version 0014 automatically (use the manual migration command above during development); earlier records are unchanged.
5. **Export product terms** ([#122](https://github.com/TaylorYam/structured-product-workflow/issues/122)): click "匯出商品條件…" beside "檢查", choose where to save and the file name (default `workflow_product_<date time>.xlsx`, starting in the last export folder), and the database's current `workflow.product` is exported whole to Excel: row 1 holds the database column names plus a final 存續狀態 (lifecycle status: 在庫／KO／接股／到期還本／顧客贖回, from the latest lifecycle event, [#152](https://github.com/TaylorYam/structured-product-workflow/issues/152), [ADR 0019](docs/adr/0019-progress-step-records-and-lifecycle-events.md); the old `status_event` columns were dropped by schema version 0020, [#172](https://github.com/TaylorYam/structured-product-workflow/issues/172)), rows are sorted by TDCC, dates and numbers keep their types, and TDCCs and other text keep their leading zeros. It only reads the database and changes nothing; unsaved edits on screen are not in the file (the completion message says so). When the file cannot be written (for example the same file is open in Excel) the reason is shown and the existing file is left untouched.

### Progress (進度)

"8 進度" lists which workflow progress stage each product is in ([#156](https://github.com/TaylorYam/structured-product-workflow/issues/156), [ADR 0019](docs/adr/0019-progress-step-records-and-lifecycle-events.md)). Click "重新整理" (refresh) to read the database; filtering and sorting happen on screen only and do not read the database again.
- Scope: every TDCC with trade rows or product terms, one row each.
- The progress is derived from database facts in order, one per product, in five stages ([#186](https://github.com/TaylorYam/structured-product-workflow/issues/186)): anything with 已寄出 (sent) is 完成 (done); a locked legacy product created by 清單更新 with no step records was finished in Excel and is also 完成 (#184); otherwise it is 資料準備中 (any of the three items needed before checking is not ready: trade rows, product terms, and prices, which run in parallel with no order) → 待核對 (all three ready, no check result yet) → 待修正 (check results but not locked) → 待寄信 (locked, no 已寄出 yet). The three items are ready when the product has trade rows; has product terms with no required field blank (a blank 期初價格 does not count once every underlying has an initial price, #182); and its check terms are 完成. The dates of preparation, return, draft creation, and the other steps are shown only and do not decide the stage.
- Columns: TDCC, issuer, trade date, days since the trade date, progress, 交易明細／商品條件／股價 (ticked when that item is ready, so a missing one stands out), lifecycle status, observation status ([#170](https://github.com/TaylorYam/structured-product-workflow/issues/170): 在庫, 等股價, 待確認, or 已出場, marked 「（未鎖住）」 when the product was not locked at observation; blank when never observed), compared through (the last date KO observation reached), observation reason, KI ([#196](https://github.com/TaylorYam/structured-product-workflow/issues/196), [ADR 0022](docs/adr/0022-pricing-status-is-ko-only.md)), objection (open objections), the date of each step (trade rows imported, product terms imported, check terms done, 已準備, checked, locked, 已放回, 草稿已建立, 已寄出; the latest when a step has several), and why it is stuck (for example no trade rows yet, the missing required fields, the reason check terms are 待確認, the check results; one entry per missing item). Stuck rows and rows whose observation status is 等股價 or 待確認 are shown in red.
- Filters: trade-date range (YYYY-MM-DD, blank means open; with a range, products without a trade date are left out), progress, lifecycle status, and observation status (multiple choice, none ticked means all; with an observation status ticked, products never observed are left out), and issuer. The default order is days since the trade date, largest first, so the products furthest behind are on top; click a heading to sort, click again to reverse, and blanks always go last.
- "匯出 Excel…" (export): writes the whole table as currently filtered and sorted to Excel (default `作業進度_<date time>.xlsx`, starting in the last export folder) with the same columns as the screen. It writes a temporary file and then renames it; when the file cannot be written (for example the same file is open in Excel) the reason is shown and the existing file is left untouched.
- The three things people may record are entered only on this tab ([#157](https://github.com/TaylorYam/structured-product-workflow/issues/157)); select products in the table first (Ctrl or Shift for several). Each writes the database in the background with who and when; a product that cannot be written affects only itself and the reason is shown; the tab refreshes afterwards:
  - "登記已寄出" (record sent): one 已寄出 step record per selected product, which makes it 完成. Before writing, the database is checked for products already recorded: if none are, one confirmation is asked; if some are, the question is Yes = record them again too, No = only those not recorded yet, Cancel = nothing.
  - "批次登記已寄出…" (batch sent, #186): when someone else does the mailing, records "everything up to this day has been sent" at once. Enter a trade date (required, YYYY-MM-DD); the database is read again, the products traded on or before that day that are currently 待寄信 (passed the check, no 已寄出 yet) are listed with their count and TDCCs, and after confirmation each gets one 已寄出; products in any other stage are left alone, and products already recorded at write time are not recorded twice. products unlocked by then are skipped too. Afterwards the status line says how many products in the same date range are not checked yet and were not recorded (products without a trade date, such as those with no trade rows yet, fall in no date range and are not counted); nothing is written when no product is 待寄信. No table selection is needed.
  - "登記顧客贖回…" (record customer redemption): enter the event date (required, YYYY-MM-DD) and a note; each selected product gets one 顧客贖回 event with source 人工; a product that already has a lifecycle event is refused with the reason. Observation stops for it afterwards.
  - "提出異議…" (raise objection): pick one product, choose one of its automatic events from observation, and write a note (required, for example what the issuer's notice says). The objection does not change the event; the "異議" column shows "待確認：event：note" until it is resolved.
  - "解除異議…" (resolve objection): pick one product and one open objection to resolve (after the data or the program is fixed and checked); who resolved it and when is recorded.

"9 出場清單" (exit list) lists the KO, 接股, 到期還本, and 顧客贖回 on one closing day ([#171](https://github.com/TaylorYam/structured-product-workflow/issues/171), [#188](https://github.com/TaylorYam/structured-product-workflow/issues/188)): after importing yesterday's closes in the morning, see which products exited yesterday.
- Enter the closing day as YYYY-MM-DD, blank meaning the latest day in the close-price table; "重新整理" (refresh) reads the database and fills the day back in, and changing the day and refreshing again shows that day. After the price backfill or the historical close import finishes observation, this tab receives the day observation reached and shows a hint bar, and "1 每日匯入" shows "下一步：出場清單 →", which switches tabs only when pressed; the list is read only on refresh.
- Current (not superseded) KO, 接股, 到期還本, and 顧客贖回 events with that event date are listed, one row per event, whatever the source: found by observation, from the old list (statuses of the former 清單更新), or a recorded 顧客贖回, so the list matches the lifecycle status on "8 進度" (#188). Events without an event date (for example some old-list 到期還本) fall on no day. Rows are ordered by event, then TDCC. The key figures are KO, 接股, 到期還本, and 顧客贖回, and the completion message gives the count per source; a day without any shows "沒有出場的商品" (no products exited).
- Columns: TDCC, issuer, product, event, event date, underlying (the worst performer for 接股), source (比價, 舊清單, or 人工), locked (已鎖住／未鎖住), and recorded at (when the event was written).
- "匯出 Excel…" (export) writes the table on screen to Excel, default name `出場清單_<closing day>.xlsx`, starting in the last export folder, with the same columns as the screen.

### Check terms

After an import on "1 每日匯入" or "2 起單資料", every **unlocked** product automatically gets the data checking needs but the order terms lack; results are written only when they differ from the last calculation ([#88](https://github.com/TaylorYam/structured-product-workflow/issues/88), [ADR 0012](docs/adr/0012-check-terms-calculation.md)). Locked products (check passed) are never recalculated. Setup automatically applies pending migrations on operator installs/updates.

- **Initial, strike, KI, and KO prices** (each underlying UL_1–UL_5): taken from the first price file dated after the Strike date, using the latest close for 收盤價 and the latest open for 開盤價. Strike/KI/KO price = raw price file value × strike/KI/KO % ÷ 100, and each of the four prices is rounded half-up to 4 decimals; the KI price is blank for barrier type NONE. With VWAP initial pricing all four stay blank (backfilled from the TS, #68) without 待確認.
- **Matching the price file**: `config/exchange_holidays.toml` must confirm that the Strike date is a trading day of the underlying's market and that no other trading day of that market lies between it and the price date (a Friday trade with Monday's file is fine; a missed day is not). Exchange codes not in the calendar (the US, Japan, and Hong Kong so far) and dates outside its range are also 待確認.
- **Branch allocation**: the product's trade rows (cancelled rows are not in the database; PB counts) summed per branch in order of appearance replace the previous allocation; mail drafts read it as before.
- **Cross-check**: currency, trade date, and UF between the trade rows and the order terms (trade rows hold a ratio such as 0.0199, the order terms percentage points such as 1.99); differences between trade rows also count. The order amount is not compared.
- **Status**: 完成 (done) / 等股價 (no price file after the Strike date yet) / 等交易明細 (no trade rows yet) / 待確認 with a reason, for example "UL_2 AAA UW：股價檔（取價日 2026-10-16）沒有這個代碼" or "UF不一致：起單資料 1.99、交易明細 0.0215（換算 2.15）". A missing code, missing price, or price conflict blanks only that underlying's prices. Prices or trade rows arriving later are picked up by the next import.
- **Missing data** ([#114](https://github.com/TaylorYam/structured-product-workflow/issues/114), [ADR 0016](docs/adr/0016-partial-product-terms.md)): the database may hold partial product terms (to be completed later on "7 人工維護"). With blank order-sheet required fields, prices and the cross-check are skipped and the status is 待確認 with the blank fields named (for example "缺 Strike (%)、Maturity date"); branch allocation is still derived from the trade rows. Once filled, the next recalculation proceeds as usual. Such products cannot be checked or released and are never backfilled or locked; mail drafts mark them 待處理 with the blank fields named. Operator installs/updates apply schema version 0012 automatically; use the manual migration command above during development, and existing data remains unchanged.
- **Releasing differences**: when a cross-check difference has been reviewed and is acceptable, select the product in the result table of "1 每日匯入" or "2 起單資料" and click "放行差異…". The Windows user name, time, and released differences are recorded and the product is recalculated; the same differences no longer block, while changed data with changed differences needs a new release. Price and calendar problems cannot be released; fix the data (for example import the missing price file).
- **Risk level** ([#238](https://github.com/TaylorYam/structured-product-workflow/issues/238), [ADR 0023](docs/adr/0023-self-calculated-risk-level.md)): the same recalculation computes RR1–RR5 with the operators' Generator spreadsheet formula: total = 0.4 × principal (always 5 for FCN) + 0.2 × tenor + 0.3 × structure (the mean of the underlying-type, underlying-count, and volatility scores plus early redemption 1, where volatility uses the mean 200-day volatility of the underlyings) + 0.1 × liquidity (0.8 × rating + 0.2); a total below 1.8 is RR1, below 2.6 RR2, below 3.4 RR3, below 4.2 RR4, otherwise RR5. Volatility is the 200日波動率 of the price file whose price date is the trade date (or the latest one before it); the rating is the guarantor's (else the issuing entity's) rating on the trade date from 「發行機構評等…」, best of the three agencies. UL_1 counts as an index when it is on the index list in `config/risk_level.toml`, otherwise as a single stock (the list is empty for now). When data is missing: trade dates before 2026-10-30 get RR4 with status 回填 (backfilled), later ones status 待算 (pending), both naming what is missing; a pending product is calculated on the next import after the data arrives. A locked product is calculated only once, while it has no risk level yet (products locked before this feature), and never changes afterwards (corrections do not recalculate it). The 風險等級 column on "2 起單資料" shows the stored value, already when reading, locked products included. The index list may say `SPX Index` or `SPX` (suffixes such as Index and Equity are dropped when matching). Results live in `workflow.risk_level`. The term-sheet / investor-information RR checks and the mail drafts use this level ([#239](https://github.com/TaylorYam/structured-product-workflow/issues/239)): the reference workbook generated from the database gains a 風險等級 column (待算 for pending), and the RR everywhere in the text, inside the fixed warnings, and in the investor-information summary is compared with it: a different RR is a mismatch, and a pending level needs manual review. Checking with an old Excel reference workbook without that column still uses the review standard's RR4. If a recalculation changes the level after checking, write-back treats the terms as changed and does not backfill (unless the checked reference workbook had no such column).
- Results live in `workflow.check_terms` (status, reason, price file used), `workflow.underlying_price` (the four prices per underlying), and `workflow.branch_allocation`; releases are in `workflow.cross_check_release`. #68 reads these tables when checking. If recalculation fails (for example a broken holiday calendar file) the import is kept and the completion message says why; importing again after the fix recalculates.

Tests (synthetic data only; real data stays local):

- `pytest -q` runs both the workflow and checker (`tests/checker/`) suites in one go. Real Word conversion tests run locally only when Word is available and are skipped in CI.
- Database tests (workflow and checker alike, marked `db`) need a disposable PostgreSQL database whose name ends in `_test`: every test drops and recreates the `workflow` and `mailbox` schemas, so never point them at the development database. Put the connection string in `SPW_TEST_DSN` (for example `host=localhost dbname=spw_test user=...`) and the password in `PGPASSWORD` (never in a file); without `SPW_TEST_DSN` they are skipped, and CI runs them against a PostgreSQL service. They share that one database: do not run them with `-n auto`, and do not let two people (or two agent sessions) run them at the same time.
- Recommended order: `pytest -q -m db` first (all database tests, serially), then `pytest -q -n auto -m "not db"` (everything else in parallel with pytest-xdist). Checker only: `pytest -q -n auto -m "not db" tests/checker`; `--shard=i/n` runs only part i (each test file stays in one part), for example `pytest -q -n auto tests/checker --shard=2/4`.
- The checker's local real-sample tests read `data/`, or set `FCN_TEST_DATA_DIR` to a folder holding `orders/` and `term-sheets/` (layout in `tests/checker/real_data.py`). The real Outlook draft test runs only when `SPW_OUTLOOK_TEST=1` is set locally (it creates and then deletes one test draft). Real-sample runs are local only: set `SPW_REAL_SAMPLES_DIR` to the folder containing product folders. CI skips all of these; real data never enters the repository, and inside the repository it stays in `FCN商品/`, which `.gitignore` excludes.
- CI picks tests from the files a PR changes (both old and new paths count when files move): documentation-only changes (`*.md`, `docs/`) run just the whitespace check; workflow-only changes (`src/sp_workflow/`, workflow tests under `tests/`, `scripts/`) skip the checker tests; checker changes (`src/fcn_checker/`, `tests/checker/`, `config/`, `panel_bootstrap.py`, `launch_checker_panel.*`, `scripts/build_panel_icon.py`) run the checker tests in 4 parallel parts; changes to `tests/conftest.py` or `tests/shard.py` run both the workflow and checker tests but not the Windows install resolution; changes to `pyproject.toml`, `constraints.txt`, CI, installer scripts, or anything unlisted run everything. Every push to `main` and every manual CI run runs everything; if the changed files cannot be listed, CI fails rather than passing with tests skipped.
